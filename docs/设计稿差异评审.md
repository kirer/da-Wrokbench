# 设计稿差异评审 · 对照《需求梳理与方案建议》v0.2

> **2026-11-22 需求澄清（重要）**：右栏复用 DSH Design Studio；UI 只保留创建迭代/需求/会话；评审、排期、范围、认领/指派等由会话 skill 完成；设计模式三态取消。《需求梳理与方案建议.md》v0.3 与《设计图交付清单.md》已同步。以下 P0-1、P0-3、P0-4、P1-7、P1-9、P1-10 等已撤回或修正，请以《设计修订说明与提示词.md》为准。

> 评审对象：`design/`（2026-11-22 稿）
> 对照文档：`需求梳理与方案建议.md`、`设计图交付清单.md`
> 结论：视觉系统和组件质量已经很高，但**第一版「需求 + 设计」闭环的核心工作界面被整体占位**，评审、排期、认领、提交/变更这些关键动作没有落稿。下面按严重程度列出差异，附文件位置和修改建议。

---

## 总体判断

**做得好的部分**

- 设计系统完整：tokens、字号、间距、状态 chip（图标 + 文字）、阶段矩阵、表格、右栏、空/错/加载/无权限态、diff、文件选择器都有样张。
- 「设计可选/并行」表达清楚：时间轴上设计轨道与开发重叠；`无需设计 / 并行 / 设计先行` 三种模式在需求卡上可见；`设计已更新` 和「评估返工」有提示；S11-003 的「开发等待设计 → 已解锁」也对。
- 「只沉淀结果」的分级表达到位：`仅本地草稿 / 已提交 / 已交付`、全量页只读、设置页文件夹说明、登录页文案都一致。
- 技能库最小版、设置、通知中心/模拟器完成度高，覆盖了版本、启用/停用、固定版本、兼容性、Mock 切换、路径校验、通知偏好等。
- 多数页面给了空态、加载、错误、无权限等变体，这是多人协作产品最容易漏的部分。

**核心问题**

设计稿把 DSH 左栏和中间会话正确识别为原生区域，但把**会话右侧的「需求/设计工作台」也一起当成了 DSH 原生区域占位**。右栏容器是 DSH 的，但工作台 tab 和内容是本插件的，恰好是第一版最核心的界面。结果是：需求怎么梳理、怎么提交/变更、设计怎么认领/出稿/交付，这些主流程在稿子里都没有可评审的界面。

## P0 · 会阻断第一版闭环

### 1. 需求工作台、设计工作台被整体占位，核心工作界面缺失

**证据**

- `design/requirement-workbench.html:48-59`：右栏标题就是「需求工作台 · 占位」，正文写「需求 / 设计工作台将基于 dsh-design-studio 改造，此处仅占位」。
- `design/design-workbench.html:48-59`：同样只有占位块。
- `design/README.md:9-11`：明确写「需求工作台、设计工作台两屏也改成占位」「本插件的真稿 = 插件页面本身」。
- `设计图交付清单.md` 的 P0 页面里，这两屏各有一整节要求：
  - 需求工作台：需求表单（背景/目标/用户故事/范围/验收标准/附件）、总述、原型画布、版本 diff、提交/变更；状态：草稿、已提交、变更中、服务端断开。
  - 设计工作台：上游需求摘要、原型、设计 brief、设计画布、设计系统/组件库、版本对比、提交设计；状态：未认领、设计中、已交付、需修改、设计先行阻塞。

> 说明：`README.md:11` 说这是「按评审意见改为占位」。如果评审意见是「不要把 DSH 原生左栏/会话画进去」，那这个边界需要修正：**右栏容器是 DSH 原生，但「需求/设计工作台」tab 和内容是本插件的**，不能和左栏/会话一起占位。另外，dsh-design-studio 主要对应设计画布/预览；需求工作台是表单 + 版本 + 提交的工作流，不应整体交给 design-studio。

**影响**

- 第一版的核心链路「建需求 → 会话 → 右栏工作台 → 技能引导 → 提交/变更」没有界面可评审，也无法据此估开发量。
- 原型画布、版本 diff、提交/变更、设计画布、设计交付、设计先行阻塞这些关键交互全部缺失。
- 后续所有页面里的「工作台」「去评审」「认领」「处理」链接都指向占位页，形成死路（见第 2、3 条）。

**建议**

- 把「DSH 原生区域」和「插件工作台」拆开：左栏和中间会话保持占位；右栏工作台按插件面板重新出稿。
- 设计画布可以继续复用 dsh-design-studio 的组件，但**工作台的面板结构、tab、表单、状态、提交动作必须由本插件设计**。
- 至少补出：
  - 需求工作台：`总述 / 原型 / 版本 / 日志` 四个 tab，或单页分区；顶部需求编号、标题、状态、提交/变更按钮；草稿/已提交/变更中/服务端断开四态。
  - 设计工作台：`上游需求 / 设计稿 / 版本 / 设计系统` 四个区；未认领/已指派/设计中/已交付/需修改/设计先行阻塞六态。
- 如果这一版不想画完整画布，可以画「工作台骨架 + 画布占位 + 状态切换」，但不能把整个工作台做成 DSH 原生占位。

### 2. 新建需求没有走「会话 + 文件夹 + 工作台」，而是跳到只读全量页

**证据**

- `design/iteration-detail.html:273-283`：新建需求弹窗只有标题；底部「创建需求」按钮链接是 `requirement-full.html`（`iteration-detail.html:282`）。
- `需求梳理与方案建议.md` §4.2：创建需求后应创建 `<top>/iterations/<迭代号>/<需求key>-<slug>/` 文件夹、创建标题为 `[S11-001] 需求名` 的 DSH 会话、自动跳转会话并打开需求工作台。
- `design/README.md:23` 说页面已串起「新建需求 → 需求工作台 / 设计工作台」，但实际链接到的是只读全量页，README 与稿子不一致。

**影响**

- 「创建需求 → 进入会话 → AI 引导梳理」这个产品最核心的入口没有表达。
- 用户创建后看到的是只读沉淀页，不能填写需求、不能保存草稿，也不知道会话/文件夹已经创建。
- 无法验证插件最关键的 DSH 能力：创建会话、命名、跳转、打开右栏面板。

**建议**

- 弹窗主按钮改为「创建并进入工作台」，跳 `requirement-workbench.html`。
- 在弹窗或创建后的过渡态里明确显示：`将创建文件夹 …/S11-007-积分任务中心/`、`将创建会话 [S11-007] 积分任务中心`。
- 补一个「创建中/创建失败（文件夹不可写、会话创建失败）」的状态；失败时保留草稿。
- 全量页只作为「已提交版本」的只读视图，不应作为创建后的落地页。

### 3. 设计任务/认领/指派流程没有落稿

**证据**

- `design/iteration-detail.html` 的需求卡上只有设计状态文字（如 S11-004 的「待认领」、S11-005 的「设计待修改」），没有设计任务卡、没有「认领 / 指派 / 开始设计」按钮。
- `design/README.md:99` 明确写「设计任务区块已去掉」。
- `design/my-workbench.html:122` 的「认领」、`:114` 的「查看」、`:130` 的「处理」全部链到 `design-workbench.html` 占位页。
- `需求梳理与方案建议.md` §4.4：迭代里应看到设计卡片；未指派可认领；指派给自己可开始设计；指派给别人只读；开始后创建 `[S11-001] 需求名 · 设计` 会话并打开设计工作台。

**影响**

- 设计师视角完全没有被设计：怎么看到任务、怎么认领、怎么被指派、怎么开始、怎么只读。
- 产品/负责人在迭代详情里也看不到设计任务的负责人、状态和待办。
- 这是第一版两个核心角色之一，不能只靠一个状态标签代替。

**建议**

- 在迭代详情补「设计任务」区块，或在每张需求卡里加一条设计任务条：设计师头像、状态、`认领 / 开始设计 / 打开工作台` 动作。
- 补「已指派」状态（当前只有待认领/设计中/已交付/待修改，缺「已指派但未开始」）。
- 认领/指派后展示「将创建设计会话」的确认，和需求创建一样落到会话 + 工作台。
- 设计师视角要有只读态：不是自己的任务时不显示「开始设计」。

### 4. 评审、排期、范围调整没有可操作界面

**证据**

- `design/my-workbench.html:106` 的「去评审」链接到 `requirement-full.html`，而全量页顶部只有「返回迭代 / 工作台 / 只读·已提交版本」（`requirement-full.html:73-76`），没有通过/打回、评论、评审人操作。
- `design/iteration-detail.html:69-79` 头部只有展示信息，没有「编辑迭代 / 改阶段时间 / 调整范围」入口；右侧「范围」卡（`:263-266`）也只有统计。
- `design/iterations.html:143-152` 的新建迭代弹窗只有编号、名称、负责人，没有阶段起止、初始范围。
- `需求梳理与方案建议.md` §3.2、§4.3、§9.4：迭代号/名称/阶段时间/范围都可改；评审页要展示最新需求、原型、影响平台，评审人评论，负责人通过/打回；通过后确定范围、阶段时间、各端负责人并锁定范围。
- `设计图交付清单.md` §3.3 明确要求「范围调整：加需求、移出需求、改阶段时间；二次确认 + 原因」。

**影响**

- 负责人/项目经理这条主线在稿子里是只读看板，不能完成「建迭代 → 定阶段 → 评审 → 排期 → 锁范围」。
- 评审是需求生命周期的关键状态（待评审/已排期），但没有任何通过/打回动作。
- 需求移出迭代、换迭代、回 Backlog（§8.3）也没有入口；第一版至少要做「提示 + 手动移动」。

**建议**

- 迭代详情头部加「编辑」：编号、名称、阶段起止、负责人；保存时提示影响范围。
- 加「排期/范围」操作：添加需求、移出需求、改阶段时间；二次确认 + 原因；范围锁定后需负责人确认。
- 补一个轻量评审面板（可以是右栏或抽屉）：最新需求、原型、影响平台、评论、通过/打回；通过后进入排期。
- 新建迭代弹窗补阶段起止和初始范围，或创建后进入「迭代设置」步骤。
- 需求移出时展示「本地文件夹/会话将如何移动」的提示，失败可重试/撤销。

## P1 · 与需求直接冲突的功能/信息缺口

### 6. 阶段矩阵缺「中台」，紧凑矩阵没有列头，3 秒看不出卡在哪

**证据**

- `design/iteration-detail.html:116-125` 每张需求卡是 8 个只有图标的 chip：需求、设计、服务端、Web、iOS、安卓、鸿蒙、测试。
- `design/app.css:468-471` 的 `.matrix--row .mx .chip .txt { display: none; }` 把文字隐藏了，只剩图标 + `title` tooltip；需求卡上没有列头。
- `design/design-system.html:259-269` 的紧凑矩阵同样只有图标 + tooltip。
- `需求梳理与方案建议.md` §2.1、§3.3：开发平台包含**中台**；阶段矩阵是「需求、设计、服务端、中台/Web/iOS/Android/鸿蒙、测试」。
- `设计图交付清单.md` §6 明确要求「一条需求卡上 8 个阶段，能不能在 3 秒内看出卡在哪」。

**影响**

- 8 个图标没有列头，用户必须逐个悬浮才知道哪一列是哪个平台，直接违背「3 秒看出卡在哪」。
- 中台是已确认支持的平台（设置页 `settings.html:102` 也有「中台」勾选），但矩阵和全量页平台卡都没有它，涉及中台的需求无法表达。
- 这是数据模型和 UI 的不一致，不是单纯的美化问题。

**建议**

- 矩阵上方加一行列头：`需求 / 设计 / 服务端 / 中台 / Web / iOS / 安卓 / 鸿蒙 / 测试`（9 列），或在 chip 内显示 2–3 字缩写（如「服」「中」「W」「iOS」）。
- 如果 9 列在 388px 右栏放不下，改成可横向滚动/两行，或提供「紧凑表格 + 展开」两档。
- 至少保留 tooltip，但不能只靠 tooltip。
- 全量页平台卡补「中台」；设置页、需求字段、矩阵三处平台列表保持一致。

### 8. 全量页版本历史错位/不一致，缺需求版本与日志

**证据**

- `design/requirement-full.html:99` 总述卡：`最新 v3`。
- `design/requirement-full.html:109-110` 原型卡：徽标 `v2`，画布标题 `prototype v2`。
- `design/requirement-full.html:113` 原型卡里的「版本历史」第一条却是 `v3 抵扣上限 / 过期提醒 · 最新`，第二条 `v2 增加过期规则`，第三条 `v1 初稿`。
- 同一页没有需求级版本历史、没有变更 diff、没有日志/时间线；设计卡（`:121`）只有 `v3 已更新`，没有设计版本列表。
- `需求梳理与方案建议.md` §9.3：全量页要有「需求总述（最新版）+ 版本历史；原型（最新 + 历史）；设计稿（最新 + 历史）+ 设计组件；…；时间线与日志」。
- `设计图交付清单.md` §3.6：全量页要有总述、原型、设计、版本、产物、日志。

**影响**

- 原型卡里的「v3」其实是需求变更（抵扣上限/过期提醒），不是原型版本；阅读者会误以为原型已经是 v3，但卡头又写 v2。
- 需求版本历史和原型版本历史混在一起，无法追溯「哪一版需求改了什么」。
- 没有日志，无法满足「一切留痕」和「可审计」。

**建议**

- 把「需求版本历史」独立成一张卡或在总述卡里展开：v1/v2/v3 + 变更原因 + diff。
- 原型卡只放原型自己的版本（v1/v2…），卡头徽标与最新版本一致；把「抵扣上限/过期提醒」这类需求变更移到需求版本历史。
- 设计卡补设计版本列表 + 对比入口。
- 全量页补日志/时间线，至少展示创建、提交、变更、设计交付、评审通过等事件。
- 如果全量页坚持只读，所有编辑动作放到工作台，但版本/日志必须可见。

### 9. 设计模式用了「仅本地」样式，语义混淆

**证据**

- `design/iteration-detail.html:114`、`:192`、`:216`：`设计模式=并行` 用了 `<span class="badge badge--local">并行</span>`。
- `design/app.css:448`：`.badge--local` 是紫色，设计系统里明确代表「仅本地」（`design-system.html:236`）。
- 同一页 `无需设计` 用普通 badge，`设计先行` 用 `badge--mock`（琥珀色），三种模式没有统一的模式样式。

**影响**

- 用户会把「并行」误读为「这条需求只在本地/未同步」，和「草稿仅本地」的含义冲突。
- 设计模式是需求的关键属性，应该有一组专门的、语义中性的 badge，而不是借用数据留存状态。

**建议**

- 新增 `badge--mode-none / badge--mode-parallel / badge--mode-before-dev`（中性色/蓝/琥珀），不要复用 `badge--local`。
- `badge--local` 只用于「仅本地草稿/未同步」。
- 在需求卡上统一显示模式，并配一句 tooltip 或图例。

### 10. `before_dev` 阻塞态、「变更待同步」没有可视状态

**证据**

- `design/iteration-detail.html:166-180`：S11-003 是「设计先行」，但显示的是「设计已交付」和「开发等待设计 → 已解锁」，没有「正在等待设计」的阻塞态。
- `design/design-system.html:246` 只有一句文字「只有 before_dev 才显示『开发等待设计』」，没有样张。
- `design/my-workbench.html:97` 有「变更待同步」，但迭代详情和全量页没有按阶段显示「变更待同步 / 已同步」的标记和确认动作。
- `需求梳理与方案建议.md` §4.4、§9.2：`before_dev` 时开发任务保持「待设计」，设计交付后解锁；需求变更后受影响阶段标记「变更待同步」，各角色确认后消失。

**影响**

- 设计先行最关键的「开发被阻塞」状态在稿子里只存在于文案，没有视觉和交互。
- 需求变更后的下游同步动作没有落稿，容易回到「需求改了，下游还在按旧版做」。

**建议**

- 补一个 `before_dev` 正在阻塞的例子：设计 chip 为「设计中」、开发 chip 为「待设计/等待设计」、卡片上有阻塞提示和「设计交付后自动解锁」说明。
- 补「变更待同步」的逐阶段标记（设计/服务端/Web/iOS…）和「确认已同步」动作；在需求卡和全量页都能看到。
- 设计工作台里也要有「设计先行阻塞」状态。

### 11. 角色权限 / 当前身份只做了局部

**证据**

- `design/iterations.html:56` 的「新建迭代」、`design/iteration-detail.html:106` 的「新建需求」在所有页面都显示，没有按当前角色隐藏/禁用。
- 登录测试用户固定为 4 人（`design/login.html:114-135`），没有「测试」角色（钱七），也没有一个多平台用户来演示多身份。
- 「当前身份」下拉只在 `design/my-workbench.html:64` 出现；迭代列表、迭代详情、技能库、设置都没有。
- `需求梳理与方案建议.md` §2.1、§2.3：一人多职能/平台，权限并集，界面显示一个「当前身份」，可随时切换；新建迭代/需求、认领设计等都有权限矩阵。
- `设计图交付清单.md` §6 要求空态/权限态齐全。

**影响**

- 设计稿无法验证「产品只能建需求、设计师只能认领设计、负责人能建迭代」这些关键权限差异。
- 多身份只在设置页勾选、我的工作台切换，其他页面看不到当前身份，容易误操作。
- 测试角色没有 Mock 用户，无法验证测试相关入口（即使第一版只留入口）。

**建议**

- 在顶栏或左栏放一个全局「当前身份」切换器，至少在我的工作台、迭代列表、迭代详情可见。
- 给出至少两套角色视角的截图/状态：产品视角（能建需求、不能建迭代）、设计视角（能认领、不能建需求）、负责人视角（能建迭代/排期）。
- 按钮按权限显示「隐藏 / 禁用 + 原因 / 可点击」三态，而不只是页面底部的无权限卡片。
- Mock 用户补测试（钱七）和一个「开发 · 服务端 + 中台 + Web」的多平台用户。

## 建议的修复顺序

1. **先补两个工作台**（需求/设计），把右栏从「DSH 原生占位」改成「插件面板骨架 + 状态」；这是第一版的核心。

3. **补评审、排期、范围调整、迭代编辑**，让负责人/PM 的主线可操作；补第一次使用的身份/文件夹向导。

5. **最后处理 P2 一致性**（技能 Phase 2 门禁、技能包、导航、Mock 用户、链接、热区规范）。
