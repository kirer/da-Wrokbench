## 3. 建数据与发布顺序

1. **张三**登录 → 首页 → 新建项目「云栖民宿」（已存在就跳过）。
2. **张三**在「云栖民宿」下依次新建 3 个迭代，填上表的编码、名称、起止日期（已存在就跳过）。
3. **李四**登录 → 切到项目「云栖民宿」→ 进入对应迭代 →「新建需求」，只填需求名称。
4. 创建后直接进入需求页，右侧是产品会话。**第一步只整理需求**：把这条需求下面
   「发给产品会话」的 `/req-start` 段发进去。模型写需求文档、复述要点和待确认项，
   这一步不出原型。
5. 文档确认后发**第二步**（每个需求都一样，下面不再重复列）：

   ```text
   /req-design
   按刚确认的需求文档出原型。
   ```

   模型一屏一个 HTML 写进这条需求的 `prototype/`，写完产品卡出现缩略图。
6. 原型确认后，李四在产品会话发送：

   ```text
   /req-submit
   ```

   提交会把当前原型固化成和需求同号的版本（第一次 v1，再提交 v2…），需求进入待评审。
7. **张三**打开这条需求（迭代评审人就是他，评审会话会自动出现），发送：

   ```text
   /lead-review approve
   ```

   通过后需求才真正发布：设计、开发、测试卡片出现，设计 / 开发卡片右上角才出现「认领」；
   测试卡要等开发完成（待测试）才出现「认领」，也可以提交时直接指定测试负责人。
8. **王五**打开需求 → 设计卡「认领」→ 确认 → 设计会话在右侧打开 → 发设计提示词；
   设计完成后在会话里执行 `/design-deliver`。
9. **孙八 / 赵六**分别打开需求 → 各自端的开发卡「认领」→ 确认 → 开发会话打开 →
   发对应端的开发提示词；完成后执行 `/dev-finish`。
10. **钱七**打开需求：测试负责人还没指定时，测试卡右上角是「认领」，确认后测试卡写钱七并准备测试会话；
    也可以直接发送 `/test-verify start`，服务端会把钱七记为测试负责人。
11. 两个开发都 `/dev-finish` → 需求进入待测试 → 钱七发测试提示词，并用 `/test-verify`
    记录开始、通过与不通过。

> 发布前只能看到产品卡片；未认领时页面没有右侧会话坞；只有被认领的那张卡才写人。
> 这些正是这轮手工验收要看的点。

## 4. 迭代一：房源与搜索（HOM-2026-12）

### 12-001 房源列表与筛选

**第一步 · 发给产品会话（李四，创建需求后发这一段）**

```text
/req-start
需求：12-001「房源列表与筛选」，先写进需求文档。
背景：用户找民宿要在多个平台比价，列表信息少，筛选后经常没有结果也不提示。
目标：一屏内按目的地、日期、人数筛出可订房源，价格与可订状态一目了然。
页面：1) 房源列表（搜索条件、房源卡片、排序、分页）；2) 筛选面板展开（价格区间、房型、设施、标签）；3) 筛选无结果空态。
状态：加载骨架、无结果、部分日期不可订、价格缺失占位。
验收：筛选条件可组合并与 URL 同步；推荐/价格/评分排序可用；卡片显示封面、标题、位置、评分、每晚价格、可订标记；空态给出放宽条件的建议。
```

**变更再出一版（还在待评审时）**

```text
/req-submit
需求：12-001「房源列表与筛选」，在 v1 上变更：分页增加「首页」「末页」。
提交前先列设计、交易服务端、Web、测试的可选人和你的建议，我选完再提交。
```

模型应先给分工建议并等选择；选定后提交，需求版本到 v2，会签按 v2 重新开始。

## 6. 迭代三：入住与评价（HOM-2027-02）

### 02-001 入住凭证与自助入住

**第一步 · 发给产品会话（`/req-start`）**

```text
/req-start
需求：02-001「入住凭证与自助入住」，先写进需求文档。
背景：入住当天用户反复问房东地址、门锁密码和停车信息。
目标：一张凭证页解决「怎么去、怎么进门、找谁」。
页面：1) 入住凭证（订单摘要、二维码/入住码、地址与导航、房东联系方式）；2) 自助入住指引（门锁步骤、Wi-Fi、停车）；3) 常见问题折叠。
```
