# 桌面端真实绘制测试方案：一个迭代两个需求（2026-S13）

> 目的：从空白数据开始，在 DSH 桌面端用**真实模型**走通「迭代 → 两个需求 → 产品原型 → 高保真设计稿 → 交付 → 预览与画布功能」。
> 上一轮只建了需求记录、画布是空的，不算通过。这一轮的核心判定是：**原型和设计稿必须由会话里的模型实际写出来**，测试脚本只输入提示词和点击，不写、不改任何产物文件。

## 1. 范围

- 被测对象：`dsh-workbench`（并入并裁剪后的设计画布 + 工作台主流程），桌面端 `desktop` profile。
- 重点：真实生成 `prototype/`（低保真原型）和 `design/`（高保真设计稿），以及交付后的跨角色预览。
- 顺带覆盖：设计画布保留的功能（首页、画布、外观、体检、导出、版本）、我的作品、需求生命周期（提交 / 评审 / 排期）。
- 不测：设计市场、灵感库、手机预览、公网分享（已裁掉）；GitLab 发布链路（`/dev-start` 起需要本地 GitLab，列为可选）。

## 2. 环境与前置

| 项 | 值 |
| --- | --- |
| 团队服务端 | `http://127.0.0.1:3210`，SQLite，mock 登录 |
| 桌面端 | DeepSeek Harness，profile `desktop`，真实模型（界面显示 DeepSeek V4.1 Flash · routing group Default） |
| 本机目录 | `~/DSH-Workbench/<迭代编码>/<需求名>/`，产物在 `prototype/` 和 `design/` |
| 驱动方式 | 桌面窗口开调试端口，Playwright 连接 CDP；只输入提示词、点按钮、截图 |
| 身份 | 张三（负责人）、李四（产品）、王五（设计）；赵六（开发）仅可选阶段用 |
| 证据目录 | `runtime/test-evidence/2026-S13-<时间>/`（`runtime/` 不入库） |

## 3. 数据重置（每次执行前）

1. 退出桌面端，停掉 3210 服务端。
2. 备份：`~/.dsh/backups/workbench-reset-<时间>/`（服务端库、`~/DSH-Workbench`、作品库、画布缓存、`local.json`）。
3. 清空：
   - `runtime/server/workbench.db*`
   - `~/DSH-Workbench/*`
   - `runtime/workbench/*`
   - `~/.dsh/dsh-workbench/canvas/{works.json,gallery-state.json}`
   - `~/.dsh/cache/dsh-workbench/*`
   - `~/.dsh/cache/dsh-workbench-poc/local.json`
   - 上一轮的 DSH 会话目录（`~/.dsh/sessions/--Users-kirer-DSH-Workbench-2026-S13--`）和 `workspace.json` 里对应的工作区条目。
4. 重启服务端（同一组环境变量），确认 `/health` 正常且种子数据为 **2 迭代 / 9 需求 / 8 用户**。
5. 重启桌面端。

## 4. 测试数据

新建迭代 `2026-S13`「积分体验优化」，下挂两个需求：

| 需求 | 端 | 原型 | 设计稿 |
| --- | --- | --- | --- |
| S13-001 积分明细页改版 | Web（1440） | 3 屏：明细列表、筛选展开、空态 | 3 屏高保真，沿用原型信息结构 |
| S13-002 积分兑换结果页 | 微信小程序（375） | 2 屏：兑换成功、库存不足/失败 | 2 屏高保真 |

### 需求简报（创建时写进活文档）

**S13-001**

```text
背景：会员反馈积分明细看不懂，抵扣和过期时间不清晰。
目标：一屏内看懂每笔积分的来源、消耗和过期时间，支持按类型筛选。
页面：1) 明细列表（余额、本月获取/消耗、类型筛选、分页）；2) 筛选面板展开态；3) 无记录空态。
状态：加载、空、筛选无结果、过期积分置灰并说明。
验收：获取/消耗/过期可区分；筛选可多选；空态有引导；金额与时间格式统一。
```

**S13-002**

```text
背景：兑换失败时用户不知道为什么，客服重复咨询多。
目标：兑换后明确告知结果和下一步。
页面：1) 兑换成功（余额变化、预计到账、查看订单）；2) 库存不足/失败（原因、替代商品、返回）。
端：微信小程序，375 宽。
验收：成功与失败状态清晰；失败给可执行建议；不引用外部图片。
```

## 5. 执行步骤

### 阶段 0：角色登录

- 张三登录，确认「迭代列表」可创建迭代。
- 李四登录，确认可新建需求。
- 王五登录，确认可创建设计会话。

### 阶段 A：产品原型（真实生成）

对 S13-001：

1. 李四在 S13 下新建需求，标题「积分明细页改版」，简报贴上方文案。
2. 创建后进入需求会话；输入框里的预填提示词应包含 `/design-start` 和「需求简报已经写进活文档」。
3. 发送预填提示词（不额外补写产物要求）。若预填缺失，发送：

   ```text
   /design-start
   需求：S13-001「积分明细页改版」
   需求简报已写进活文档，请调用 workbench_design_context 读取。
   在 prototype/ 下生成低保真产品原型，一屏一个 HTML，共 3 屏：明细列表、筛选展开、空态。
   只写 prototype/，不要写 design/，不要调用交付工具。
   ```

4. 等待模型完成（会话出现「已完成，用时 …」），检查：
   - `~/DSH-Workbench/2026-S13/积分明细页改版/prototype/*.html` 至少 3 个。
   - 文件 mtime 落在本轮模型执行期间；会话记录里能看到写文件的工具调用。
   - 单文件、内联 CSS/JS、无外部资源；黑白灰低保真。
5. 打开右侧「需求」面板，确认画布列出 3 屏且能切换；截图。
6. 对 S13-002 重复 1–5（2 屏：兑换成功、库存不足/失败）。

### 阶段 B：高保真设计稿（真实生成 + 交付）

对 S13-001：

1. 王五打开需求 →「新建会话」→「设计会话」。
2. 输入框预填的设计模板里补齐四项：

   ```text
   - 要设计的页面 / 流程：积分明细列表 → 筛选 → 空态，沿用 prototype/ 的信息结构
   - 关键状态：默认、加载、空、筛选无结果、过期
   - 视觉方向：沿用积分业务品牌蓝与中性灰，信息密度中高，数字等宽
   - 端与交付范围：Web 1440，3 屏
   ```

   末尾保留「加载 ui-design 技能，一屏一个 HTML 写进 design/ …… 再用 /design-deliver 交付」。
3. 先发送 `/design-claim` 认领设计：右栏应从「设计稿只读预览」切到可编辑的设计画布。认领后再发送设计提示词；模型写完 `design/`。
4. 等待完成，检查：
   - `design/*.html` 至少 3 个，内容为高保真（真实文案、品牌色、层级/状态完整）。
   - 右侧「设计」面板自动显示，画布可切屏；截图。
5. 发送 `/design-deliver`，确认：
   - 需求设计状态变为「已交付」，设计版本 `d1`，交付人王五。
   - 服务端记录了交付文件（数量与 `design/` 一致）。
6. 对 S13-002 重复（2 屏，小程序 375）。

### 阶段 C：交付面与画布功能

1. 换李四 / 张三登录，打开同一需求的「设计」面板：应看到服务端交付版本（不是本机文件），预览走 `/dsh-workbench/api/design-preview`，画面完整。同目录的 `tokens.css` / `app.css` 要随交付一起上传并在预览里内联，页面不能是无样式 HTML，也不能被 CSP 拦掉样式。
2. 需求详情：设计状态、设计师、版本历史、交付时间显示正确。
3. 我的作品：设计目录出现在作品库，缩略图为该设计第一屏；接口 `works` / `workthumb` 返回 200。
4. 设计画布（王五本机）：
   - 首页、画布、外观、体检、导出、版本入口齐全。
   - 「体检」能返回结果（允许有提示项，不能报错崩溃）。
   - 「导出」生成 zip 到 `~/Downloads`，解压后包含各屏 HTML 和清单。
   - 确认画布内没有「手机预览」「设计市场」「灵感」入口。
5. 记录所有截图与命令输出。

### 阶段 D：生命周期（可选，核心完成后执行）

## 8. 失败处理

- **模型没写文件 / 写偏目录**：截图 + 保存会话记录，停止，不手工补文件；可用更窄的提示词重试一次（新建会话），仍失败判失败。
- **模型超时**：单轮等待上限 15 分钟；超时视为失败并记录当时的画布与文件状态。
- **桌面端 / 服务端异常**：按备份恢复后重来，不带着半成品继续。
- **回滚**：`~/.dsh/backups/workbench-reset-<时间>/` 里的服务端库、`DSH-Workbench`、作品库、画布缓存和 `local.json`。

## 9. 时间与成本

- 约 30–50 分钟：两次原型（5 屏）+ 两次设计（5 屏）+ 交付与验证。
- 模型调用发生在桌面端真实模型上，按会话轮次计费；测试只发送阶段 A/B 的必要提示词。

## 10. 固定脚本

方案已经固化成两个可重复执行的脚本，不再用一次性 Playwright 片段：

| 脚本 | 作用 |
| --- | --- |
| [`tools/reset-workbench-test-data.sh`](../tools/reset-workbench-test-data.sh) | 备份并清空测试数据，重启服务端（种子基线）和桌面端（9222 调试端口） |
| [`e2e/desktop-s13.mjs`](../e2e/desktop-s13.mjs) | 登录、建迭代与两个需求、发提示词、等待模型完成、校验文件/交付/作品/画布，输出报告 |

```bash
# 清空测试数据并重启（破坏性：会退出桌面端、删除 ~/DSH-Workbench 下的测试数据）
bash tools/reset-workbench-test-data.sh

# 预检：服务端、桌面端、登录、基线是否为 2 迭代 / 9 需求
node e2e/desktop-s13.mjs --preflight

# 只建迭代和两个需求，停在提示词（不调用模型；跑完要重置）
node e2e/desktop-s13.mjs --prepare

# 只验证已有交付：跨角色预览、我的作品、缩略图（不调用模型）
node e2e/desktop-s13.mjs --verify

# 全流程（约 30–50 分钟）
node e2e/desktop-s13.mjs

# 一条命令：重置 + 全流程
node e2e/desktop-s13.mjs --reset
```

脚本的硬约束：

- 只输入提示词、点击和截图；**不写、不改 `prototype/`、`design/` 里的任何文件**。
- 产物验收看三样：目录里的 HTML、文件时间、会话记录；模型没画出来就判失败。
- 证据写到 `runtime/test-evidence/2026-S13-<时间>/`，包含截图、需求草稿、会话尾部、
  文件清单、服务端状态和 `report.md` / `report.json`。
- 失败不补产物；重试只能新开会话再让模型画一次。
