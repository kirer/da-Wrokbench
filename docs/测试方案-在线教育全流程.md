# 在线教育全流程测试方案

这份方案把「项目 → 迭代 → 需求 → 各角色进入自己的工作」串成一条可重复的测试链路。
结构层由 `e2e/check-online-education.mjs` 自动跑；需要真实模型产出原型 / 设计稿的步骤
在方案里单独标出，避免把模型波动混进流程回归。

## 0. 准备

```bash
# 清空测试数据并重启服务端 + 桌面端（会退出桌面端，破坏性操作）
bash tools/reset-workbench-test-data.sh

# 跑结构全流程
node e2e/check-online-education.mjs
```

`--reset` 可以在跑测试前自动清空：

```bash
node e2e/check-online-education.mjs --reset
```

前置：DSH 桌面端已开 `9222`，服务端在 `127.0.0.1:3210`，插件已安装当前 `client.js`。
证据写到 `runtime/test-evidence/online-education-<时间>/`（截图、状态、报告）。

## 2. 测试流程

### 阶段 1：项目

- 张三新建项目「在线教育」。
- 期望：项目菜单出现「在线教育」，切换后首页的迭代列表为空（新项目还没有迭代）。

### 阶段 2：迭代

- 张三新建迭代：
  - 迭代编码：`EDU-2026-11`
  - 迭代名称：`初始化项目`
  - 开始日期：当天
  - 结束日期：留空
- 期望：迭代创建后自动切换；开始日期落库，结束日期为空；迭代目录在顶级文件夹下创建。

### 阶段 3：需求

- 李四在「初始化项目」下建两个需求：
  1. **课程列表**：只填名称，不再补充，用来观察“还没开始工作的需求”。
  2. **课程详情与报名**：创建后在产品会话里讲清需求（背景、目标、页面、状态、验收），用来走完整生命周期。
- 期望：
  - 创建需求后停在需求页，产品会话在右侧坞里，不跳去 DSH 的会话工作区；
  - 会话输入框保持为空；对话上方出现引导消息，带需求编号、标题和要做的端，并用一段示例说明需求可以怎么讲；
  - 通用的原型规则由 `/design-start` 技能提供，不写进输入框；
  - 需求说明由产品会话写进需求活文档；
  - 「课程列表」停在草稿，没有提交版本、没有原型文件；
  - 「课程详情与报名」有 `folderPath`、`prototype/`、`design/` 目录和产品会话。

### 阶段 4：草稿需求的卡片墙

- 李四重新进入「课程详情与报名」（还没发布）。
- 期望：
  - 总述占满一行，显示需求说明；
  - 只有一张产品卡片，显示负责人李四和原型屏数；
  - 页头不出现「设计 / 未认领 / 设计状态」，空需求不假设一定涉及设计；
  - 不出现设计、开发、测试卡片，也不显示“不涉及平台”；
  - 卡片墙下方提示“需求还没有发布”。

### 阶段 5：发布（当前由接口完成）

产品在会话里完成梳理和原型后，提交需求；负责人评审通过。

当前测试直接调用接口，因为新需求页还没有评审入口：

1. 李四提交：`POST /requirements/{id}/submit`
2. 张三评审通过：`POST /requirements/{id}/review { decision: "approve" }`

评审全部通过时服务端会自动把需求纳入本期范围；期望需求从草稿 → 待评审 → 已通过，
版本号和评审记录落库。发布后重新打开需求页，页头才出现设计信息，设计、开发、测试卡片才出现。

> 缺口：发布时“指定一部分端、指定一部分人”还没有接口和 UI。当前端在创建需求时按
> 产品身份默认（李四是交易服务端 + Web），人员靠 `design-claim` / `dev-claim` 认领。

### 阶段 6：设计

- 王五进入「课程详情与报名」。
- 期望：
  - 卡片墙上没有王五：进入需求页不预建会话，右侧也不显示会话坞；
  - 设计卡右上角的状态徽标是「认领」按钮；
  - 点「认领」弹「认领这个任务？」，确认后设计卡显示王五，同时创建并打开设计会话；
  - 设计会话上方是带需求标题、端和产品原型屏数的设计引导（用示例说明想要的设计可以怎么讲），输入框为空；
  - `打开设计画布` 可点；
  - 设计画布打开后，面包屑当前层是「设计」，右侧会话坞仍在。

真实设计稿的生成由会话里的模型完成（`/design-start` → 写 `design/` → `/design-deliver`），
不属于结构层脚本的断言范围。

### 阶段 7：开发

- 孙八、赵六分别进入需求。
- 期望：
  - 本人负责、还没人认领的端（孙八是 Web，赵六是交易服务端），卡片右上角是「认领」按钮；
  - 未认领时右侧不显示会话坞；点「认领」确认后，对应端的任务设为“已指派”，开发卡片显示负责人，并创建、打开开发会话；
  - 开发会话里可以用 `/dev-start`、`/dev-finish` 推进。

当前脚本只验证“卡片上认领 + 卡片 + 会话”，不启动模型写代码。

### 阶段 8：测试

- 钱七进入需求。
- 期望：测试没有「认领」这一步，进入需求就自动准备测试会话；测试卡片随第一轮测试出现负责人。
- 测试轮次由 `/test-verify` 驱动（内部调用开始测试、通过或不通过的工具）。

### 阶段 9：空需求

- 李四再次查看「课程列表」。
- 期望：仍是草稿，版本数 0，原型 0 屏，卡片墙显示「原型 0 屏」和“还没开始”。

## 3. 引导消息与技能的边界

会话输入框不再预填模板，用户进来直接描述需求。开场白是一条真实的 assistant 消息，
放在对话上方：先报需求编号、标题和要做的端（设计会话还报产品原型屏数），
再用日常说话的方式说明可以怎么讲、给一段示例，最后说清聊完之后会产出什么。

示例只演示「谁在用、现在哪儿不顺手、希望做成什么」这种讲法，不是让产品照着填；
页面、状态、异常由会话追问。通用的产出规则放在 `/design-start` 技能里，
不在每条开场白或输入框里重复：

- 原型 / 设计稿写哪个目录、一屏一个 HTML、文件名用中文；
- 原型是「左原型 + 右需求说明」的双栏文档，右栏包含哪些章节；
- 低保真原型的黑白灰规则、单文件内联资源、画布自动刷新；
- 设计稿加载 `ui-design`、交付走 `/design-deliver`。

这样产品只需要补完需求描述，模型按技能规则产出；改规则时只改技能，不改每个需求的提示词。

## 4. 当前缺口

| 缺口 | 现状 | 建议 |
| --- | --- | --- |
| 需求评审页面 | 接口和 `/req-review` 技能可用，需求页没有入口 | 在需求页加评审卡片 / 操作，或在产品卡片里放“提交 / 评审”动作 |
| 工作量评估 | 需求模型没有字段，页面没有入口 | 增加评估卡片（人天、按端拆分、评估人、更新时间） |
| 发布指定端和人 | 创建需求时按产品身份默认端，人员靠认领 | 发布技能接收 `platformIds` 和 `assignees`，服务端落 dev_tasks |
| 真实原型 / 设计稿 | 结构层脚本不调用模型 | 用 `e2e/desktop-s13.mjs` 或手动在会话里发提示词 |

## 5. 通过标准

- 结构脚本 10 个步骤全部通过，报告里没有失败截图；
- 两个需求的状态符合预期（一个草稿、一个已发布）；
- 每个进入需求的角色都有自己的会话，且会话坞不需要手动创建；
- 需求页卡片墙能显示每个人的工作面入口；
- 缺口清单与实际一致（如果后续补上评审 / 工作量 / 发布范围，测试要同步更新断言）。
