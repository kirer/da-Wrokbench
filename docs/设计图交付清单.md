# DSH 研发工作台 · 设计图交付清单

> 依据《需求梳理与方案建议》v0.3；与《设计修订说明与提示词.md》一致，冲突时以修订说明为准。
>
> 第一版范围：**需求 + 设计**。开发、测试、封板只在信息架构里预留入口，不出细稿。
>
> 目标：按这份清单可以直接出 Figma / 蓝湖稿，交付给开发实现。

---

## 1. 设计前先知道的 6 件事

1. **产品形态**：DSH 插件。左侧栏是主页面入口，中间是会话，右侧是随会话打开的工作台；桌面端按 1440×900 设计，右栏宽 360–420px。
2. **右栏 = DSH Design Studio**：需求/设计右栏基于 Design Studio 改造，外观和交互以它为准；本插件不重新设计画布，只加需求上下文和「进入会话/在会话中提交」入口。
3. **第一版用户**：负责人/项目经理、产品、设计。开发/测试身份可以登录，但只看到预留入口和「Phase 2/3」提示。
4. **设计是可选的、默认并行**：不再有「不需要 / 并行 / 设计先行」三态，也没有 designMode 选择器。设计稿没出，也可以评审、排期，甚至先开发；只有 skill 明确标记「等待设计」时，对应开发任务才等设计。设计晚到标「设计已更新」。
5. **UI 只保留三个写入口**：创建迭代、创建需求（只输入名称）、创建会话。评审、排期、范围调整、设计认领/指派/开始、需求提交/变更、设计交付都由会话里的 skill 完成；UI 负责看状态和「进入会话」。
6. **只沉淀结果 + 钉钉先 Mock**：草稿留在本地，提交/交付后的版本才进服务端；登录页要有 Mock 模式提示和测试用户选择，正式钉钉登录界面保持一致，只换 Provider。

## 3. 每个页面的关键点

### 3.1 登录与首次使用

- 登录方式：钉钉扫码 / Mock 选人；两种模式共用同一布局。
- 首次使用独立 onboarding，不要登录后直接进迭代列表：
  - Step 1 身份：职能（负责人/项目经理、产品、设计、开发、测试、管理员）多选；平台/团队按服务端配置动态展示、可多选；选一个「当前身份」。
  - Step 2 文件夹：本地目录选择器；显示路径、可写徽标、磁盘空间；错误态（不存在/不可写/权限不足）。
  - Step 3 确认：当前身份、文件夹、Mock/正式模式摘要；「进入工作台」；可返回修改。
- 平台不要写死：中台不一定有，服务端/前端可能拆多个团队。示例：服务端组（交易/商品/用户）、前端组（Web/小程序）、客户端组（iOS/Android/鸿蒙）；中台组如启用才显示。
- Mock 模式横幅：说明「当前为测试登录，不会连接钉钉」；正式模式不显示。

### 3.2 迭代列表

- 卡片或表格；字段：迭代号、名称、当前阶段、起止时间、负责人、需求数、进度、风险提示。
- 主按钮：新建迭代（仅负责人/项目经理可见）。
- 筛选项：我参与的、进行中、已封板。

### 3.3 迭代详情

- 头部：迭代号/名称（可编辑）、负责人、状态、范围锁定提示。
- 时间轴：需求与评审、设计、开发、测试、封板；**设计轨道允许与需求/开发重叠**，不要画成严格串行。
- 需求列表/卡片：一行或一张卡一个需求。阶段矩阵只渲染该需求实际涉及的平台，按平台组分组；平台多时用「服务端 3」汇总 + 展开，不涉及的平台折叠成一行「不涉及：商品服务端、Android…」。
- 矩阵必须有列头，不能只靠 tooltip；服务端组平台额外有「接口已就绪」，其他组没有。
- 设计不在迭代详情做独立任务区块；需求卡只显示设计状态（无需设计 / 待认领 / 设计中 / 已交付 / 设计已更新）。
- 日志：谁在什么时候创建/提交/变更/指派；右侧或底部抽屉。
- 范围摘要：当前范围、锁定状态、最近调整；加需求/移出需求/改阶段时间由会话 skill 完成，UI 只保留「进入会话」，不做表单。
- 评审/排期同样走会话 skill；迭代详情只显示状态、时间轴和范围摘要。

### 3.4 新建需求

- 弹窗只保留「需求名称」；不要放设计模式、平台范围、负责人、优先级、描述。
- 点击「创建需求」后展示后台步骤：创建文件夹 → 创建会话 → 打开会话/DSH Design Studio；用户不需要关心中间过程。
- 状态：创建中、创建失败（文件夹不可写/会话创建失败，保留输入可重试）、重复标题提示。
- 落地页改为自动创建的会话/Design Studio，不要跳只读的 `requirement-full.html`。
- 设计是否需要、是否等待设计、涉及哪些平台/团队、各平台负责人、优先级，全部由 `/req-draft` 在会话里询问。

### 3.5 需求工作台（右栏）

- **此处为 DSH Design Studio + 需求上下文，不重新设计画布。**
- 顶部上下文条：需求编号、标题、状态、当前版本；插件加的「在会话中提交/变更」入口。
- 内容：需求总述、原型预览、版本/日志；需要画布时进入 Design Studio。
- 不在这里做需求表单、保存草稿、提交评审、变更需求等表单；这些由 `/req-draft`、`/req-submit`、`/req-change` 在会话里完成。
- 版本：当前版本、历史版本、diff 只读展示；草稿版本只在本地。

### 3.6 需求全量页

- 总述（最新版）、原型、设计稿、设计组件、接口文档（预留）、Bug（预留）、版本历史、日志。
- 各端卡片按平台组分区，不要平铺 3 列把服务端/前端/客户端/测试混在一起；不涉及的平台折叠成一行，不占整卡。
- 每张平台卡建议包含：
  - 头部：平台组 · 平台/团队名、状态、负责人、「进入会话」。
  - 时间：计划开始/结束、实际开始、预计完成；逾期/风险标识。
  - 关键产物：服务端展示接口文档版本/就绪状态、commits/MR、下游前端依赖；前端/客户端展示设计稿版本、接口就绪情况、目标设备/端、commits/MR；测试展示用例进度、Bug 汇总、提测环境。
  - 依赖/阻塞：等待设计/接口/其他平台；风险提示。
  - 最近更新：相对时间 + 最近事件。
  - 动作：只放「进入会话」；未指派写「待认领 · 进入会话认领」，不加表单。
- 只展示「已提交/已交付」的版本；草稿不在这里出现。
- 设计未交付时显示「待认领/设计中」，设计晚到显示「设计已更新」，不要显示空白。

### 3.7 设计工作台（右栏）

- **此处为 DSH Design Studio + 上游需求，不重新设计画布。**
- 上游需求摘要、原型、设计 brief；Design Studio 的画布、版本对比、设计体检、设计系统/组件库入口、导出。
- 认领、指派、开始设计由 `/design-claim`、`/design-assign` 在会话里完成；UI 不提供认领按钮，只显示状态和「进入会话」。
- 提交设计：在会话里 `/design-submit` 选择要交付的版本 → 填 changelog → 上传/链接 → 提交；UI 只显示「在会话中提交」入口。
- 不再显示「设计先行模式阻塞」；只有需求卡/开发任务上的「等待设计」「设计已更新」状态。

### 3.8 技能库（最小版）

- 列表：按角色/平台筛选，技能卡显示名称、版本、适用角色/平台、状态。
- 详情：描述、版本、changelog、内容预览、兼容性。
- 操作：启用/停用、固定版本、查看版本历史。
- 第一版不做个人上传入口，但页面结构要能容纳（灰置或「Phase 2」提示）。

### 3.9 设置

- 身份与平台/团队、顶级文件夹、认证模式（Mock/钉钉）、通知偏好、技能更新策略。
- 管理员增加「平台配置」：平台组和平台/团队的新增、改名、排序、归档；中台组默认可以不存在。
- Mock/正式切换要有明确提示和不可用原因。

## 4. 全局组件

- 状态 chip：需求/设计/各平台/测试；颜色区分「未开始 / 进行中 / 已完成 / 阻塞 / 不涉及」。
- 阶段矩阵：按需求实际涉及的平台动态渲染，按平台组分组；平台多时汇总 + 展开，不涉及折叠；必须有列头，不能只靠 tooltip。
- 平台卡：平台组 · 平台/团队、状态、负责人、计划/实际时间、关键产物、依赖/阻塞、最近更新、「进入会话」。
- 版本 diff：需求/设计/技能三类复用同一套对比组件。
- 指派/认领：头像、角色、状态、可认领提示；认领/指派动作在会话 skill，不在 UI 做表单。
- 技能卡：名称、版本、适用角色/平台、状态、使用量。
- 空状态 / 错误状态 / 加载态 / 权限不足 / 服务断开。
- 文件/文件夹选择器（本地路径、多项目）。
- Mock 模式横幅（醒目但不刺眼）。

## 5. 出图约定

- 桌面端 1440×900；右栏 360–420px；遵循 DSH 现有布局与主题变量，浅色/深色都要。
- 中文界面；文案要能直接用于实现。
- 每个页面标注：默认态、空态、加载态、错误态、无权限态、操作成功/失败提示。
- 第一版不需要出开发/测试工作台细稿，但信息架构里要能看到入口和「Phase 2/3」标记。
- 右栏明确标注复用 **DSH Design Studio**，不重新设计画布；平台配置驱动矩阵和卡片，不要写死平台列。
- 交付 Figma/蓝湖链接 + 组件库 + 标注；如果沿用 design-studio 的设计 token，请注明来源。

## 6. 评审时重点看什么

1. **设计默认并行是否一眼看懂**：设计没出时，评审和开发是否还能继续；设计晚到时是否知道要返工；明确等待设计时是否只影响对应开发任务。
2. **平台组/团队是否清楚**：不同服务端团队、不同前端/客户端是否分得开；平台多时矩阵是否还能在 3 秒内看出卡在哪；不涉及的平台是否折叠。
3. **右栏是否不抢主会话**：Design Studio 是辅助，不是第二个后台；插件只加上下文和入口。
4. **写入口是否够少**：除了创建迭代/需求/会话，评审、排期、范围、认领/指派等是否都收在会话 skill 里，UI 没有多余表单。
5. **技能库是否可管理**：版本、角色/平台包、启用/停用是否清楚。
6. **空态/错误态/权限态是否齐全**：这是多人协作产品最容易漏的部分。
