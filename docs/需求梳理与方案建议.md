# DSH 部门研发工作台 · 需求梳理与方案建议

> 版本 v0.3 · 2026-11-22
>
> v0.3 修订：平台改为可配置的「平台组 + 平台/团队」；移除 designMode 三态；评审/排期/范围/认领等写操作统一由会话 skill 完成；右栏需求/设计工作台基于 DSH Design Studio，不单独做表单。
>
> v0.2 补充：设计可选/可与评审开发并行、技能管理模块、服务端只存沉淀数据、钉钉 Mock 可测试方案、设计图交付清单。
>
> 目标：把「迭代制研发流程」变成 DSH 里的部门工作台。结构化数据负责流程、权限与留痕；DSH 会话负责 AI 协作；技能负责把对话结果写回流程。

> **已确认（2026-11-22）**
> - 共享数据：**团队服务端**（内网部署；DSH 插件仍是主界面）。
> - 身份模型：**多身份**（职能 + 可配置平台/团队，可多选，权限取并集）。
> - 平台模型：**两级可配置**（PlatformGroup 平台组 + Platform 平台/团队）；服务端/前端可拆多个团队，中台可选。
> - 第一版范围：**只做「需求 + 设计」**；开发、测试、封板后置。
> - 工程方式：**在当前目录创建自有改造**；设计画布参考 dsh-design-studio，记忆参考 dsh-mnemon + dsh-mmpl，按需复制模块并记录上游。
> - 设计：**可选、默认并行**；不引入 designMode；明确等待设计时用任务状态「等待设计」。
> - 服务端数据：**只存沉淀结果**（提交版本、交付物、事件元数据、提炼后的记忆），不存个人完整会话和过程草稿。
> - 技能：新增**技能管理模块**，支持版本、角色技能包、个人上传与审核。
> - 钉钉：先用**可切换的 Mock Provider** 开发测试，拿到凭据后切正式 Provider。

---

## 0. 结论先行

1. **它不是「再做一个 Jira」，而是「迭代协作台 + 每个角色的 AI 工作入口」。** 需求、设计、开发、测试各自在自己的 DSH 会话里干活，工作台负责状态、产物和日志。
2. **必须有团队服务端。** DSH 是装在每个人电脑上的单机工具，迭代、需求、指派、Bug、日志这些多人共享数据必须有一个共同的事实源；钉钉的 AppSecret 和 GitLab 回调也不能放在客户端。DSH 插件仍然承担几乎全部用户界面和 AI 交互，服务端是「无界面的协作后端」。
3. **身份建议拆成「职能 + 可配置平台/团队」，并支持一人多身份。** 例如一个人可以同时是「开发 · 交易服务端」和「开发 · Web」，权限取并集，当前身份可切换。不要把职能做成互斥单选，也不要把平台写死。
4. **需求不要只维护一个大状态，而要「生命周期状态 + 阶段矩阵」。** 矩阵按该需求实际涉及的平台动态生成，并按平台组（服务端 / 前端 / 客户端…）分组；整体状态由阶段推导。这样才不会状态爆炸。
5. **工程在当前目录自建改造，按需借鉴 design-studio 与 dsh-mmpl。** 设计画布以 dsh-design-studio 为上游参考，记忆分层与注入参考 dsh-mmpl；只复制真正需要的模块，保留上游同步记录。
6. **第一版只做「需求 + 设计」闭环。** 开发、提测、Bug、封板后置；自动录屏、完整记忆、发版再往后。第一版选一个真实小组，把「建迭代 → 建需求 → 需求工作台 → 设计认领 → 设计工作台 → 提交/变更」跑通。
7. **设计不是串行门槛，也不做「设计模式」。** 需求可以先评审、先排期、甚至先开发；设计默认是可选的并行轨道。确实要等设计时，由 skill 把开发任务标成「等待设计」；设计晚到则标「设计已更新」。
8. **服务端只沉淀结果。** 会话全文、草稿、多个原型草稿留在本地；只有确认提交的版本、交付物、事件元数据和提炼后的记忆进服务端。
9. **技能是资产，要独立管理。** 技能库要有版本、角色技能包、个人上传、审核、回滚和使用统计；每个会话固定技能版本，保证可复现。
10. **钉钉先 Mock。** 用同一套 AuthProvider 接口先做可测试的本地登录/组织架构/通知模拟，拿到企业应用凭据后无缝切换。

### 一张图看懂

```text
迭代
 ├─ 需求（产品）── 评审/排期 ── 设计（设计师，可选/默认并行）
 │                                └─ 服务端接口文档（接口先行）
 ├─ 开发（按平台配置：交易服务端 / 商品服务端 / Web / iOS / Android…）
 │        └─ 逐端提测
 ├─ 测试（用例 / Bug / 复测）
 └─ 封板
       每个环节 = 工作台卡片 + DSH 会话 + 技能回写 + 日志 + 产物
```

> 第一版覆盖图中「迭代 → 需求 → 设计」这一段；开发、测试、封板是后续阶段。

## 1. 产品定位与边界

### 1.1 是什么

- **迭代协作台**：迭代、需求、范围、排期、各端任务、Bug、封板，一个地方看清。
- **AI 工作入口**：每个角色从自己的任务卡片一键进入专属 DSH 会话，技能带着上下文引导完成工作。
- **产物与留痕中心**：原型、设计稿、接口文档、代码提交、测试用例、Bug 录屏，都挂在需求上，永远可追溯。
- **部门记忆**：把规范、技术栈、组件库、历史决策沉淀下来，新会话自动带上。

### 1.2 边界（第一版 vs 整个产品）

> 第一版只做「需求 + 设计」；开发、测试、封板、发版是后置阶段，不是砍掉。

| 不做 | 用什么代替 |
|---|---|
| 完整项目管理（成本核算、OKR、财务） | 只做研发协作所需的最小集 |
| CI/CD、发版、部署 | 预留 Release 对象和扩展点，Phase 4 再做 |
| 代码托管、MR 管理 | GitLab，工作台只存链接和状态 |
| 设计工具本身 | Figma / 蓝湖 / MasterGo / design-studio，工作台存链接与版本 |
| IM | 钉钉，工作台只发通知 |
| 通用低代码/表单引擎 | 不为每个字段做配置器，先固定模型 |

### 1.3 设计原则

- **一个事实源**：共享数据以服务端为准；本地只放工作副本、会话和代码。
- **对话即操作**：技能和按钮能完成的，不让用户手填第二遍。
- **一切留痕**：创建、变更、指派、提交、提测、Bug、封板都有事件。
- **只看与自己有关的**：「我的待办」优先，迭代详情再展开全量。
- **可撤销、可审计**：移出迭代、变更、封板都要能回退或至少留痕。

## 2. 角色与身份

### 2.1 职能与平台分离

| 维度 | 取值 | 作用 |
|---|---|---|
| **职能** | 部门负责人 / 项目经理、产品、设计、开发、测试、管理员 | 决定权限和工作台类型 |
| **开发平台** | 两级可配置：平台组（服务端、中台、前端、客户端…）+ 平台/团队（交易服务端、商品服务端、Web、小程序、iOS…） | 决定开发任务卡片、提测卡片和阶段矩阵 |
| **身份呈现** | 职能 +（开发时）具体平台/团队 | 例如「开发 · 交易服务端」「开发 · Web」 |

规则：

- 一个人可以勾选多个职能/平台，**权限取并集**。
- 界面上仍显示一个「当前身份」，用于默认打开哪个工作台、默认过滤哪些任务；可随时切换。
- 平台用**两级配置**，不写死枚举：
  - **PlatformGroup**：服务端、中台、前端、客户端……管理员可新增/改名/排序；中台不一定有，默认种子可以不放，需要时再启用。
  - **Platform**：挂在组下的具体平台/团队，如交易服务端、商品服务端、用户服务端、Web、小程序、iOS、Android、鸿蒙；可新增/改名/排序/归档，归档不删除历史数据。
- 需求 `platformScope[]` 存具体 `PlatformId`；开发任务 = 需求 × 平台；身份也选具体平台。
- 测试、设计是阶段，不是平台组；不要为了凑矩阵把它们做成平台。
- 角色、平台组、平台都放在服务端配置表里，管理员可增删改，不在代码里写死。

对应的配置对象：

```text
PlatformGroup { id, name, order, active, supportsApiDoc }
Platform      { id, groupId, name, shortName, order, active/archived }
```

> 「服务端组」在代码里指 `supportsApiDoc=true` 的接口型平台组，不靠组名硬编码；矩阵的「接口已就绪」、下游依赖和接口文档都按这个标记判断。默认种子把服务端组设为 `true`，中台/前端/客户端为 `false`。

默认种子示例（可以按团队实际改）：

```text
服务端组：交易服务端、商品服务端、用户服务端
前端组：Web、小程序
客户端组：iOS、Android、鸿蒙
中台组：默认不启用（有独立中台团队时再加）
```

### 2.2 登录与首次使用

```text
首次打开插件
  → 钉钉扫码 / 授权登录
  → 服务端用 AppSecret 换用户信息与部门
  → 返回短期插件 token
  → 选择职能 / 具体平台（按组展示，可多选）
  → 选择个人顶级文件夹
  → 完成，进入工作台
```

要点：

- **AppSecret 只在服务端**，客户端只拿短期 token；token 过期自动续。
- 钉钉应用需要企业管理员开通通讯录权限；组织架构定时同步到服务端，人员搜索走服务端。
- 个人顶级文件夹、项目目录只存在本地，不上传真实路径；服务端最多存「已配置」标记。
- 如果公司已有统一 SSO，可以替换钉钉登录，但建议保留钉钉作为身份源和组织架构源。

### 2.3 权限矩阵（建议）

| 能力 | 负责人/项目经理 | 产品 | 设计 | 开发 | 测试 | 管理员 |
|---|:---:|:---:|:---:|:---:|:---:|:---:|
| 创建/编辑迭代、改阶段时间 | ✓ |  |  |  |  | ✓ |
| 确定迭代范围、移出需求 | ✓ | 建议 |  |  |  | ✓ |
| 创建需求 |  | ✓ |  |  |  | ✓ |
| 提交/变更需求 |  | ✓ |  |  |  | ✓ |
| 认领/提交设计 |  |  | ✓ |  |  | ✓ |
| 认领/评估/开发/提测 |  |  |  | ✓（本平台） |  | ✓ |
| 提 Bug、复测、关闭 Bug |  | 可选 | 可选 |  | ✓ | ✓ |
| 修复 Bug、转交 Bug |  |  |  | ✓（被指派） |  | ✓ |
| 封板 | ✓ |  |  |  | ✓（确认） | ✓ |
| 角色/平台/集成配置 |  |  |  |  |  | ✓ |

> 说明：产品是否能改迭代范围，取决于你们的管理习惯；建议「产品提议、负责人确认」。

### 2.4 钉钉接入：Mock 优先，可切换

现在拿不到钉钉企业应用凭据，不应该阻塞开发。做法是把认证抽成 Provider，先用 Mock 跑通全部流程。

```ts
interface AuthProvider {
  id: 'dingtalk' | 'mock'
  getLoginUrl(state: string): string
  exchangeCode(code: string): Promise<TokenSet>
  getUser(userId: string): Promise<User>
  listDepartments(): Promise<Department[]>
  searchUsers(query: string): Promise<User[]>
  sendNotification(userId: string, message: Notification): Promise<void>
}
```

| Provider | 用途 | 行为 |
|---|---|---|
| **MockProvider** | 开发、演示、自动化测试 | 内置测试用户（产品/设计/开发/测试/负责人）、模拟部门树；登录页选人即可；通知写入 outbox + 站内通知中心 |
| **DingTalkProvider** | 生产 | 钉钉 OAuth2 授权码换 token；通讯录同步；工作通知；服务端持有 AppSecret |

规则：

- **正式 DingTalkProvider 照常实现**，不因为先上 Mock 而简化；Mock 只是同一接口的另一实现。
- `AUTH_PROVIDER=mock` 只在开发/测试环境允许；生产启动时发现 mock 直接拒绝启动，并打印醒目的警告。
- Mock 签发**真实 JWT**，claims 与正式 Provider 完全一致；权限、身份切换、审计都按正式逻辑走，不能因为是 Mock 就绕过。
- 通知在 Mock 模式下写入 `notification_outbox` 表 + 控制台 + 插件内「通知模拟器」页，方便验证指派、变更、提测等消息。
- 提供种子数据与重置脚本：一个迭代、两个需求、产品/设计/负责人各一人。
- 两套 Provider 跑同一组契约测试；切换只改环境变量，不改业务代码。

以后拿到钉钉应用后需要提供：CorpId、AppKey、AppSecret、AgentId、登录/通讯录权限、回调地址、管理员授权。这些只放服务端环境变量，不进仓库。

## 3. 核心对象

### 3.1 对象总表

| 对象 | 作用 | 关键关系 |
|---|---|---|
| **Iteration 迭代** | 一次研发周期的容器 | 包含多个需求；有阶段与起止时间 |
| **Requirement 需求** | 业务需求的主对象 | 属于一个迭代（或 Backlog）；派生设计任务、各端开发任务、测试任务 |
| **PlatformGroup / Platform 平台组/平台** | 可配置的组织维度 | 平台属于平台组；需求选择具体 Platform；DevTask 挂在 Platform 上 |
| **DesignTask 设计任务** | 一个需求的设计工作 | 一个需求最多一个；可指派/认领 |
| **DevTask 开发任务** | 一个需求在一个平台上的开发工作 | 每个「需求 × 涉及平台」一条 |
| **TestTask 测试任务** | 一个需求的测试工作 | 一个需求一个；包含用例与 Bug |
| **Bug** | 测试发现的缺陷 | 属于需求与某个平台；可转交、重开 |
| **Artifact 产物** | 原型、设计稿、接口文档、提交、MR、用例、录屏等 | 挂在需求/任务/Bug 上，带版本 |
| **Event 事件/日志** | 谁在什么时候做了什么 | 所有对象的变更都产生事件 |
| **SessionLink 会话关联** | 某个用户某个角色与 DSH 会话的绑定 | 本地会话 ID + 文件夹路径 |
| **MemoryItem 记忆** | 部门/项目/迭代/需求/个人知识 | 由记忆系统管理 |

### 3.2 迭代（Iteration）

| 字段 | 说明 |
|---|---|
| `id` | 稳定内部 ID，永不变 |
| `code` | 迭代号，如 `2026-S11`，可改；改后保留旧号映射 |
| `name` | 迭代名称，可改 |
| `ownerId` | 负责人（钉钉用户 ID） |
| `status` | `planning` 规划中 / `active` 进行中 / `frozen` 已封板 / `released` 已发版（预留）/ `archived` 已归档 |
| `phases[]` | 阶段列表：需求与评审、设计、开发、测试、封板；每项有计划开始/结束、实际开始/结束 |
| `requirementIds[]` | 迭代范围 |
| `members[]` | 参与人及角色快照 |
| `scopeLockedAt` | 范围锁定时间（建议开发开始时锁定） |
| `createdAt / updatedAt` | 审计 |

规则：

- 迭代号、名称、阶段时间、范围都可改，但**每次修改都写事件**，并通知受影响的人。
- 阶段「实际时间」尽量由事件自动推导：首个需求提交、首个设计交付、首个开发开始、全部提测、封板。
- 需求可以移出迭代（去 Backlog 或另一个迭代），规则见 §8.3、§9.2。

### 3.3 需求（Requirement）

| 字段 | 说明 |
|---|---|
| `id` | 稳定内部 ID |
| `key` | 人类可读编号，如 `S11-001`；建议稳定，改标题不改 key |
| `title` | 需求名，可改 |
| `iterationId` | 所属迭代；可为空（Backlog） |
| `creatorId / ownerPMId` | 创建人 / 产品负责人 |
| `summary` | **需求总述（Living Spec）**，持续更新，不是一次性文档 |
| `platformScope[]` | 涉及平台：具体 `PlatformId[]`，从服务端平台配置里选 |
| `priority` | P0–P3 或自定义 |
| `status` | 生命周期状态，见下 |
| `versions[]` | 需求版本快照 |
| `artifacts[]` | 原型、设计、接口文档、提交、录屏等 |
| `sessionRefs[]` | 各角色会话关联 |
| `createdAt / updatedAt` | 审计 |

> 设计不是评审/排期的前置条件，也不引入 `designMode` 字段。设计是否参与由 skill 在会话里询问：存在 DesignTask 即表示需要设计。默认设计与开发并行、不阻塞；只有明确要求等待设计时，才把相关 DevTask 标为「等待设计」。

#### 需求生命周期（建议最小集）

```text
创建中 draft
  └─ /req-submit → 待评审 submitted
        ├─ 评审通过 → 已排期 planned
        │     └─ 设计/开发开始 → 进行中 in_progress
        │           └─ 全部涉及平台提测 → 待测试 ready_for_test
        │                 └─ 测试开始 → 测试中 testing
        │                       └─ 测试通过 → 已完成 done
        │                             └─ 封板 → 已封板 frozen
        └─ 评审不通过 → 修改中 changes_requested → 回到待评审
异常：已移出迭代 moved_out / 已取消 cancelled / 挂起 on_hold
```

> 建议不要把「设计中」「开发中」「测试中」做成互斥大状态。需求同一时间可能设计和开发并行（不同平台），所以用下面的**阶段矩阵**表达进度，整体状态只做汇总。

#### 阶段矩阵（卡片上的 chips）

| 阶段 | 状态 |
|---|---|
| 需求 | 创建中 / 待评审 / 已通过 / 变更待同步 |
| 设计 | 无需设计 / 待认领 / 已指派 / 设计中 / 已交付 / 待修改 / 设计已更新 |
| 平台（需求 `platformScope[]` 中的每个 Platform 一条，按 PlatformGroup 分组） | 不涉及 / 待认领 / 待评估 / 开发中 / 接口已就绪（仅接口型平台组）/ 已提测 / 测试中 / 完成 |
| 测试 | 未开始 / 用例就绪 / 测试中 / 阻塞 / 通过 / 封板 |

整体状态由这些阶段推导，避免手动维护一个永远对不上的大状态。

矩阵渲染规则：

- 只渲染该需求实际涉及的平台，按平台组分组；服务端组、前端组、客户端组的顺序和名称都来自平台配置。
- 平台多时按组汇总（如「服务端 3」）并可展开；不涉及的平台折叠成一行「不涉及：商品服务端、Android…」。
- 接口型平台组（`supportsApiDoc=true`，默认是服务端组）额外有「接口已就绪」状态；其他组没有，不要给所有平台套同一套状态。
- 测试、设计是阶段，不是平台组。

### 3.4 任务

> 第一版只实现 DesignTask；DevTask / TestTask 先建数据模型，Phase 2/3 再实现 UI 与流程。

#### 设计任务 DesignTask

| 字段 | 说明 |
|---|---|
| `requirementId` | 所属需求 |
| `assigneeId` | 指派设计师；为空表示可认领 |
| `status` | 待认领 / 已指派 / 设计中 / 已交付 / 待修改 |
| `versions[]` | 设计稿版本（链接或文件） |
| `designSystemRef` | 使用的设计系统/组件库 |
| `submittedAt` | 交付时间 |

> 认领 / 指派 / 开始设计都由会话 skill 完成；UI 只在需求卡上显示设计状态，不单独做设计任务区块。

#### 开发任务 DevTask（每个需求 × 平台一条）

| 字段 | 说明 |
|---|---|
| `requirementId` + `platformId` | 唯一键；`platformId` 来自平台配置 |
| `assigneeId` | 指派或认领 |
| `estimate` | 工时评估（人天/人时 + 置信度 + 备注） |
| `status` | 等待设计（仅明确要求等待设计时）/ 不涉及 / 待认领 / 待评估 / 开发中 / 接口已就绪（仅接口型平台组）/ 已提测 / 测试中 / 完成 |
| `repos[]` | 该任务关联的本地项目目录（仅本地保存路径；服务端存仓库标识） |
| `apiDoc` | 接口型平台组（`supportsApiDoc`）产出的接口文档（链接 + 版本 + 就绪状态） |
| `commits[] / mrs[]` | 提交与合并请求链接，只追加不覆盖 |
| `testEnv` | 提测环境地址（可选） |
| `submittedAt` | 提测时间 |

> 默认不设「等待设计」；只有 skill 明确把任务标成等待设计时，设计交付后才转「待认领 / 待评估」。设计晚交付时，已开始的开发任务标「设计已更新」，由 skill 评估返工，不把开发倒回阻塞态。

#### 测试任务 TestTask

| 字段 | 说明 |
|---|---|
| `requirementId` | 所属需求 |
| `assigneeId` | 测试负责人 |
| `cases[]` | 测试用例（最小结构化集，或文档链接） |
| `status` | 未开始 / 用例就绪 / 测试中 / 阻塞 / 通过 / 封板 |
| `freezeSignoff` | 封板确认人/时间 |

### 3.5 Bug

| 字段 | 说明 |
|---|---|
| `key` | `BUG-0001` |
| `requirementId` | 所属需求（也允许「非需求 Bug」，挂到迭代） |
| `platformId` | 具体平台 ID（来自平台配置，不是固定枚举） |
| `title / description` | 标题、复现步骤、期望/实际 |
| `severity` | 阻塞 / 严重 / 一般 / 轻微 |
| `reporterId / assigneeId` | 提出人 / 当前处理人 |
| `status` | 新建 / 已指派 / 修复中 / 待复测 / 已关闭 / 已重开 / 已转交 / 非缺陷 / 延期 |
| `repro` | 录屏、截图、日志、环境信息 |
| `commits[]` | 修复提交链接 |
| `verifyNote` | 复测结论 |
| `events[]` | 指派、转交、重开等记录 |

Bug 生命周期：

```text
新建 → 已指派 → 修复中 → 待复测 → 已关闭
                    │         └─ 复测不通过 → 已重开 → 修复中
                    ├─ 转交 → 已指派（新处理人）
                    ├─ 非缺陷 → 关闭
                    └─ 延期 → 挂起（需负责人确认）
```

### 3.6 产物（Artifact）与事件（Event）

| 产物类型 | 内容 | 版本策略 |
|---|---|---|
| `prototype` | 原型 HTML / 设计稿预览 / 链接 | 每次提交存一版 |
| `design` | 设计稿链接或导出图 | v1, v2… |
| `design-system` | 组件库/设计规范引用 | 引用式，不复制 |
| `api-doc` | 接口文档链接（Swagger/YApi/GitLab Wiki） | 版本 + 就绪状态 |
| `commit` / `mr` | GitLab 提交/合并请求链接 | 不可变，只追加 |
| `test-case` | 用例集 | 版本 |
| `recording` | Bug 复现录屏 | 附件 |
| `spec-snapshot` | 需求总述的版本快照 | 每次提交/变更 |

事件统一结构：`actor / action / targetType / targetId / before / after / summary / timestamp / source`。迭代详情的「日志」就是按迭代过滤的事件流。

> 产物只存「确认提交/交付」的版本；同一会话里的多个草稿留在本地，不上传服务端（详见 §9.5）。

## 4. 六条主流程

### 4.1 创建迭代（负责人 / 项目经理）

1. 迭代列表 → 新建迭代：填迭代号、名称、负责人、阶段与计划起止时间。
2. 系统生成默认阶段模板（需求与评审 / 设计 / 开发 / 测试 / 封板），可改。
3. 迭代进入 `planning`；成员收到钉钉通知（可选）。
4. 后续任何字段修改都写事件；阶段时间变更通知全员。

### 4.2 需求创建与交付（产品）

1. 在迭代详情点「新建需求」，填标题。
2. 插件检查个人顶级文件夹 → 创建需求文件夹与会话：
   - 文件夹：`<top>/iterations/<迭代号>/<需求key>-<slug>/`
   - 会话标题：`[S11-001] 需求名`
   - 自动跳转到该会话，右侧栏打开基于 DSH Design Studio 的需求工作台/上下文。
3. 迭代里出现需求卡片，状态「创建中」；日志记录「谁创建了什么需求」。
4. 会话里的技能引导逐步完成：
   - `/req-draft`：背景、目标、用户故事、范围、验收标准、附件；
   - 询问：需要设计吗？如果要，是否等设计交付再开发？涉及哪些平台/团队（从平台配置里选，可多选）？各平台指定谁？优先级？
   - 需要原型时，调用设计画布的预览工具在工作台画布出原型。
5. `/req-submit`：
   - 校验必填项（设计不是必填；等待设计的阻塞发生在开发开始时，不在提交时）；
   - 生成需求 v1 快照；
   - 状态 → 待评审；
   - 按回答生成设计任务（可为空）、各平台开发任务（未指派为「待认领」；明确等待设计的初始为「等待设计」）；
   - 日志记录「谁交付了什么需求」；
   - 通知评审人。
6. 变更：`/req-change` 生成 vN+1，记录 diff 与原因，标记受影响阶段「变更待同步」，通知相关角色（见 §9.2）。

> 评审和排期不等待设计。设计可以在需求提交后随时开始/认领，与评审、排期并行；只有明确等待设计时，才阻塞对应开发任务。

### 4.3 评审与排期（负责人 + 各端技术负责人；工时评估在 Phase 2）

1. 评审在需求会话里进行：skill 展示需求最新版、原型、影响平台；不单独做评审页。
2. 评审人在会话里评论；负责人用 `/req-review` 通过或打回（skill 调用工具回写状态）。
3. 通过后，各平台开发收到工时评估任务：
   - `/estimate` 引导填人天/人时、置信度、依赖与风险；
   - 评估结果汇总到排期视图。
4. 负责人根据评估敲定（`/iteration-plan` 回写）：
   - 真正进入迭代的需求范围；
   - 各阶段开始/结束时间；
   - 各平台负责人（可后续认领）。
5. 需求状态 → 已排期；迭代范围锁定（`scopeLockedAt`）。

> 第一版只做评审通过与进入迭代；工时评估、排期视图随开发阶段（Phase 2）实现。

> **设计不是评审/排期的前置条件。** 评审看需求本身；默认设计与评审/排期并行，排期不标注设计模式。只有明确等待设计时，对应开发任务保持「等待设计」；设计晚交付时标「设计已更新」。

> 评审保持轻量：会话里一个通过/打回动作 + 评论即可，不搞复杂审批流；UI 只显示评审状态和「进入会话」。

### 4.4 设计（设计师）

设计是否参与由 `/req-draft` 询问，不在需求上存 `designMode`。存在 DesignTask 就表示需要设计；没有就显示「无需设计」。

| 情况 | 评审/排期 | 开发 | 设计交付后 |
|---|---|---|---|
| 不需要设计 | 不依赖 | 立即可开始 | — |
| 需要设计（默认并行） | 不依赖 | 可从需求/原型开始 | 已开始的开发任务标「设计已更新」，评估返工 |
| 明确等待设计 | 不依赖 | 等设计交付再开始 | 开发按设计开始 |

> 设计可以在需求提交后随时开始，不必等评审通过；评审和设计可以并行。认领/指派/开始设计都在会话里由 skill 完成，UI 不单独做设计任务区块。

1. 需求卡上显示设计状态（无需设计 / 待认领 / 设计中 / 已交付 / 设计已更新）。设计师从需求卡或通知进入需求会话，用 `/design-claim` 认领，或由负责人用 `/design-assign` 指派；UI 不提供认领按钮。
2. 开始工作时（skill 执行）：
   - 在需求文件夹下建 `design/` 子目录；
   - 创建会话 `[S11-001] 需求名 · 设计`；
   - 右侧栏打开 **DSH Design Studio**：上游需求、原型、设计系统、画布，外观和交互以 Design Studio 为准。
3. 设计过程：
   - 参考/复用 design-studio 的设计范式、画布、版本对比、设计体检、导出；
   - 技能 `/design-brief` 可把需求转成设计 brief；
   - 设计系统/组件库从部门记忆或项目配置里带出。
4. `/design-submit`：
   - 发布设计稿到共享存储（或填外部链接）；
   - 生成设计 vN；
   - 需求卡设计状态 → 已交付；
   - 日志 + 通知产品/开发。
5. 设计变更：重新提交生成 vN+1，受影响开发任务标记「设计已更新」。

### 4.5 开发与提测（各端开发 · Phase 2）

1. 需求卡片显示各平台 chip；被指派或可认领（认领动作走会话 skill）。
2. 开始工作：
   - 若没有工时评估 → 先 `/estimate`，未评估不能进入开发；
   - 首次开发需选择项目目录（可多个），插件记住，可随时改；
   - 创建会话 `[S11-001] 需求名 · 服务端`（同理 Web/iOS/…）；
   - 右侧栏打开「开发工作台」：任务、需求、接口文档、项目文件树、提交记录。
3. 接口型平台组先行（通常是服务端）：
   - `/api-doc` 产出/更新接口文档；
   - 标记「接口已就绪」，通知下游前端可以开始对接。
4. 开发过程可用各种开发技能；代码提交：
   - `/dev-submit-code`：检查分支、提交、推送，可选创建 MR；
   - 把 commit/MR 链接追加到开发任务；
   - 不改变提测状态。
5. `/dev-ready-for-test`：
   - 校验至少有一个代码链接（或标记不涉及）；
   - 填写提测环境、自测结论、已知风险；
   - 平台卡片 → 已提测；
   - 日志 + 通知测试/产品；
   - GitLab 链接一并挂到需求产物里。
6. 所有涉及平台都提测后，需求 → 待测试；测试阶段可以开始。

> 服务端接口文档建议作为一等公民：前端可以在接口文档就绪后先行开发，不必等后端全部完成。

### 4.6 测试、Bug 与封板（测试 / 开发 · Phase 3）

1. 测试从需求或测试工作台进入，创建会话 `[S11-001] 需求名 · 测试`。
2. `/test-plan`（可选）：根据需求和验收标准生成测试用例草稿，测试编辑确认。
3. `/bug-report`：
   - 结构化表单：标题、平台/团队、严重程度、复现步骤、期望/实际、环境、附件；
   - 默认指派给该平台开发；
   - 日志 + 通知。
4. `/bug-record`（Phase 3）：
   - Web：Playwright 录屏 + 控制台/网络日志；
   - 移动端：后续接 adb / 模拟器录屏；
   - 录屏自动作为 Bug 附件。
5. 开发收到 Bug：
   - 一键打开修复会话（关联需求、复现录屏、项目目录）；
   - `/bug-fix` 引导定位、修复、提交；
   - 提交链接挂到 Bug；
   - 状态 → 待复测，或填写原因后转交。
6. 测试 `/bug-verify`：
   - 通过 → 已关闭；
   - 不通过 → 已重开，回到修复中。
7. `/iteration-freeze`：
   - 校验：所有涉及平台已提测、阻塞/严重 Bug 已关闭（一般/轻微可有条件遗留）；
   - 测试 + 负责人确认；
   - 迭代 → 已封板，需求 → 已封板；
   - 生成封板报告：需求清单、各端提交、Bug 统计、已知问题、产物链接；
   - 之后默认只读，确需修改要负责人解锁并留痕。


## 6. 技能体系

### 6.1 技能清单（建议）

| 技能 | 角色 | 作用 | 写回 |
|---|---|---|---|
| `/req-draft` | 产品 | 引导梳理需求、生成总述草稿 | 需求草稿 |
| `/req-submit` | 产品 | 校验并提交需求 v1 | 需求状态、任务、日志 |
| `/req-change` | 产品 | 变更需求，生成新版本与 diff | 版本、影响标记、通知 |
| `/req-review` | 负责人/评审人 | 评审通过/打回、评论 | 需求状态、日志 |
| `/iteration-plan` | 负责人/产品 | 调整迭代范围与阶段时间（排期） | Iteration.scope/phases、事件 |
| `/design-claim` | 设计 | 认领设计任务 | DesignTask.assignee/status |
| `/design-assign` | 负责人/产品 | 指派设计师 | DesignTask.assignee |
| `/design-brief` | 设计 | 需求转设计 brief | 设计任务备注 |
| `/design-submit` | 设计 | 发布设计稿、生成版本 | 设计任务、产物 |
| `/estimate` | 开发 | 引导工时评估 | DevTask.estimate |
| `/api-doc` | 服务端 | 产出/更新接口文档 | DevTask.apiDoc |
| `/dev-submit-code` | 开发 | 提交代码、记录 commit/MR | DevTask.commits |
| `/dev-ready-for-test` | 开发 | 提测校验与状态更新 | DevTask、需求状态 |
| `/bug-report` | 测试 | 结构化提 Bug | Bug、通知 |
| `/bug-record` | 测试 | 自动录屏复现（Phase 3） | Bug 附件 |
| `/bug-fix` | 开发 | 修复引导、提交、转交 | Bug 状态、commits |
| `/bug-verify` | 测试 | 复测通过/重开 | Bug 状态 |
| `/iteration-freeze` | 测试/负责人 | 封板检查与报告 | 迭代/需求状态 |

> 第一版实现：`/req-draft`、`/req-submit`、`/req-change`、`/req-review`、`/iteration-plan`（最小排期）、`/design-claim`、`/design-assign`、`/design-brief`、`/design-submit`。其余随对应阶段实现。

命名建议：**英文命令 ID + 中文显示名**，避免中文命令在不同终端/输入法下出问题。

### 6.2 实现原则

- **技能负责「问」和「引导」，工具负责「写」。** 所有写操作走插件注册的工具（如 `workbench_create_requirement`、`workbench_submit_design`），由服务端做权限、校验、日志；技能不直接改文件/数据库。
- **技能是主入口；UI 只保留创建迭代/需求/会话等少数写入口。** 不在 UI 里为每个技能再做一套表单；状态和结果由技能回写后展示。
- **技能返回结构化结果**，工作台据此刷新，不靠解析自然语言。
- **错误可恢复**：提交失败保留草稿，不丢用户输入。

### 6.3 技能管理模块（新增）

技能是「可执行的流程资产」，不只是提示词。不同角色/平台需要不同组合，技能会持续演进，个人经验也需要沉淀和审核。只把 `SKILL.md` 放在文件夹里不够，需要独立的技能库。

### 6.4 对象模型

| 对象 | 关键字段 | 说明 |
|---|---|---|
| **Skill** | id、名称、显示名、描述、分类、适用角色/平台、标签、owner、可见性、状态、最新版本 | 技能主对象 |
| **SkillVersion** | skillId、版本号、内容（SKILL.md + 资源）、changelog、内容哈希、兼容 DSH 范围、状态、作者、发布时间、测试报告 | 不可变；每次修改产生新版本 |
| **SkillPack** | id、名称、角色/平台、items[{skillId, versionId}]、版本、状态 | 角色技能包，锁定具体版本 |
| **SkillInstall** | userId、skillId、versionId、启用、锁定、安装时间 | 个人安装状态 |
| **SkillUsage** | sessionId、skillId、versionId、requirementId、结果、反馈 | 使用统计与效果反馈 |
| **SkillReview** | versionId、审核人、结论、意见 | 团队发布审核 |

### 6.5 版本与生命周期

```text
draft 草稿 → in_review 审核中 → published 已发布 → deprecated 已废弃
                     └─ rejected 打回 → draft
```

- 版本不可变；编辑 = 新版本。必须填 changelog。
- 支持版本 diff、回滚（把旧内容作为新版本重新发布）、按版本安装/锁定。
- 兼容性：声明支持的 DSH 版本范围；安装时校验，避免升级 DSH 后技能失效。
- 废弃：指定替代技能与迁移说明；已锁定旧版本的会话不受影响。
- 内容哈希：本地缓存按哈希校验，防止内容漂移。

### 6.6 角色/平台技能包

| 技能包 | 典型技能 |
|---|---|
| **产品包** | 需求梳理、用户故事、验收标准、需求变更、竞品分析 |
| **设计包** | 设计 brief、设计交付、设计评审、设计转规格、设计系统检查 |
| **服务端包**（可按团队拆：交易 / 商品 / 用户） | 接口文档、服务端 code review、数据库迁移、服务端测试计划 |
| **前端包**（Web / 小程序，可按端拆） | 按设计稿开发页面、Web code review、组件库使用、性能检查 |
| **客户端包**（iOS / Android / 鸿蒙，可按端拆） | 按设计稿开发原生页面、各端 code review、平台规范、打包检查 |
| **中台包**（可选，仅有中台团队时启用） | 共享能力接入、中台接口规范、中台 code review |
| **测试包** | 测试计划、用例生成、Bug 提交、复测、回归 |
| **通用包** | 提交信息规范、变更日志、风险检查 |

- 技能包按**平台组或具体平台**配置，不写死「服务端/Web/iOS」；平台新增/改名/归档后，包跟着配置走。
- 每个包有版本，锁定内部技能的具体版本；会话创建时记录「用了哪个包版本」，保证可复现。
- 管理员可以「强制」或「推荐」某个包；个人可以增删，但不能破坏强制项。
- 开发各端的 code review、按设计图开发页面等技能，放在对应平台包里；这是后续开发阶段的主要入口。

### 6.7 个人上传与审核

- 上传格式：`SKILL.md` + 资源文件（zip 或在线编辑）；填写名称、描述、适用角色/平台、可见性、许可证。
- 个人技能默认**私有**，可本地安装；提交团队发布后进入审核队列。
- 自动校验：frontmatter 完整、命令名不冲突、资源路径合法、体积限制、密钥/令牌扫描、危险命令扫描、外部 URL 白名单。
- 预览与试用：渲染 SKILL.md，在测试会话里跑一遍，附示例输出。
- 审核：团队技能需要 owner + 审核人；支持 diff、评论、通过/打回；全程审计。
- 权属：上传即授权团队使用；记录许可证；禁止上传含密钥、个人隐私或公司敏感数据的内容。

### 6.8 与 DSH 的对接

DSH 从文件系统或 Skill Provider 加载 `SKILL.md`。建议两种方式并存：

| 方式 | 用途 | 做法 |
|---|---|---|
| **动态 Skill Provider** | 团队技能 | 插件像 design-studio 一样注册 provider，按会话/角色返回锁定的版本；不落盘、不冲突 |
| **本地物化** | 个人技能、离线 | 同步到 `~/.dsh/workbench/skills/<name>/<version>/SKILL.md`，由 DSH 文件系统技能加载 |

- 会话固定技能版本；升级需要用户确认或管理员策略。
- 命令名保持稳定；重命名保留别名，避免旧会话失效。
- 离线时用最后一次安装的版本；服务恢复后校验哈希并提示更新。
- 安装前做 DSH 版本兼容检查。

### 6.9 页面与交互

| 页面 | 内容 | 关键动作 |
|---|---|---|
| **技能库** | 按角色/平台/状态/owner 筛选；搜索；技能卡（版本、使用量、状态） | 安装、启用、试用、查看详情 |
| **技能详情** | 描述、适用角色、版本列表、changelog、内容预览、使用统计、兼容性 | 安装/启用、上传新版本、废弃 |

| **上传/编辑** | 文件或在线编辑、元数据、校验结果、预览 | 保存草稿、提交审核 |

### 6.10 数据与 API（建议）

- 内容存内容寻址 blob（按哈希），元数据存数据库；可选 Git 备份/导出，方便审计与迁移。
- 主要接口：`GET/POST /skills`、`GET /skills/:id`、`POST /skills/:id/versions`、`POST /skill-versions/:id/submit|publish|reject`、`POST /skills/:id/install`、`GET/POST /skill-packs`、`GET /skill-usage`。
- 权限：个人技能本人可写；团队技能需审核；管理员可强制包、废弃技能、查看审计。
- 审计：上传、审核、发布、安装、废弃都写事件；不记录技能运行中的完整会话内容。

## 7. 记忆系统（Phase 2，先定架构）

> 第一版不做记忆实现；但需求/设计会话已经需要「上下文包」，所以先把架构定下来，避免以后返工。

### 7.1 两条参考路线

| 参考 | 可借鉴什么 | 注意 |
|---|---|---|
| **dsh-mnemon** | Sources / Strategy / View 组合；Project Documents、Memory Spaces；`extension-sdk` 可扩展部门 Source | 偏「上下文编排」，检索后端可换 |
| **dsh-mmpl** | L0→L1→L2→L3 分层；常驻热记忆注入；每轮自动捕获；遗忘曲线/记忆宫殿；技能库 | 依赖外部 MMPL 服务（Rust/DuckDB + 向量检索），部署多一个组件 |

建议：**存储与检索放工作台服务端**（Postgres + pgvector，或直接复用 MMPL），**插件侧只做注入与捕获**。这样部门记忆、需求记忆和迭代数据在同一个权限体系里；如果团队更想要现成的向量检索与遗忘机制，可以把 MMPL 作为记忆后端。

### 7.2 分层（借 mmpl 的思路）

| 层 | 内容 | 示例 |
|---|---|---|
| **L0 原始** | 会话轮次、事件、提交、评论 | “产品说积分过期规则改成 12 个月” |
| **L1 事实/决策** | 从 L0 提炼出的稳定事实 | “积分有效期 = 12 个月，2026-11-22 确认” |
| **L2 场景** | 需求/迭代/项目的上下文包 | S11-001 的背景、约束、相关人 |
| **L3 画像** | 部门/项目/个人长期画像 | 部门技术栈、设计规范、个人偏好 |

- 检索：关键词 + 向量 + 融合排序；带来源链接。
- 遗忘：过期/低价值记忆进归档区，可恢复，不直接删除。
- 热记忆：每个角色会话注入一小段（部门规范、当前迭代约束、需求摘要）。

### 7.3 记忆范围与权限

| 范围 | 内容 | 存储 | 谁能写 |
|---|---|---|---|
| **L0 原始对话** | 会话全文、未提炼内容 | 本地 | 本人（不上传） |
| **个人记忆** | 偏好、常用命令、当前身份 | 本地 | 本人 |
| **部门记忆** | 流程规范、角色职责、术语表、质量门禁、技术栈 | 服务端 | 管理员/负责人审核 |
| **项目记忆** | 仓库架构、接口规范、构建/发布方式、坑点 | 服务端 | 技术负责人 |
| **迭代记忆** | 范围、决策、风险、复盘 | 服务端 | 负责人/产品 |
| **需求记忆** | 总述、决策、变更、Bug 模式 | 服务端 | 产品/测试/开发协作 |

> 服务端只存提炼后的 L1–L3；L0 原文留在本地。记忆抽取默认在本地完成，只上传结论。

### 7.4 注入与捕获（插件侧）

- 注入：`ctx.systemPrompt.section()` + `variable()` 注册热记忆段；mmpl 已验证该用法。
- 捕获：`ctx.on('session/event')` 在 `turn/end` 把用户/助手关键内容写入 L0，去重、截断。
- 工具：`memory_search / memory_write / memory_manage`，技能可调用。
- 失败降级：记忆服务不可用时静默跳过，不阻塞主流程。

### 7.5 注入策略

- 产品会话：部门流程 + 相似历史需求 + 术语表。
- 设计会话：需求 + 设计系统 + 品牌规范 + 历史设计。
- 开发会话：需求 + 接口文档 + 项目规范 + 相关代码/提交。
- 测试会话：需求 + 验收标准 + 历史 Bug 模式 + 用例模板。
- 新会话创建时自动带「需求上下文包」，而不是让用户每次重复背景。

### 7.6 治理

- 团队记忆默认「AI 起草 + 人审核」，防止错误记忆污染全员。
- 记忆必须带来源链接（需求/文档/会话），可编辑、可删除、可回滚。
- 不存密钥、令牌、个人隐私；项目路径不跨人共享。
- 记忆与当前指令冲突时，**当前指令优先**。

## 8. 会话、文件夹与项目目录

### 8.1 目录结构（建议）

```text
<个人顶级文件夹>/
  iterations/
    2026-S11/
      S11-001-会员积分改版/
        req/            # 需求总述、原型、附件
        design/         # 设计稿、导出、组件引用
        dev/            # 开发笔记、接口文档副本
        test/           # 用例、录屏、Bug 附件
        workbench.json  # 本地索引（会话 ID、对象 ID；非权威数据）
  backlog/
  archive/
```

- 权威数据在服务端；本地目录是工作副本和产物落盘处。
- 文件夹名用 `key-slug`，标题改了不轻易改文件夹名，避免引用失效。
- `workbench.json` 只存本地映射（sessionId、对象 ID、最近同步时间），可重建。

### 8.2 会话规则

- **一个角色任务一个会话**：需求、设计、每个开发平台、测试、每个 Bug 修复，都可以有独立会话。
- 会话标题统一：`[S11-001] 需求名 · 设计` / `· 服务端` / `· 测试`。
- 会话 cwd 建议 = 需求文件夹；代码仓库作为 **additional directories** 挂进来（DSH 已支持多目录），这样产物和代码都在一个会话里。
- 如果 DSH 的多根目录在插件 API 上不够用，降级为：每个仓库一个会话 + 需求工作台做关联（见 §12 D5）。
- 插件负责创建会话、命名、打开；已核实 DSH 客户端 bundle 中存在 `sessions.create`、`renameSession`、`additionalDirectories` 能力，但公开 API 稳定性需要 POC。

### 8.3 需求移出迭代 / 换迭代

| 情况 | 处理 |
|---|---|
| 还没开始任何下游工作 | 直接移动；更新服务端；本地文件夹移动到目标迭代目录；无会话影响 |
| 已开始设计/开发 | 标记任务 `paused/moved`；通知相关人；文件夹移动；会话如果正在运行，延迟到空闲再移动，或新建会话并归档旧会话 |
| 换到另一个迭代 | 保留需求 ID、版本、提交、Bug；重算阶段日期；评估是否需要重新排期 |
| 回 Backlog | 移动到 `<top>/backlog/`；保留所有产物链接；任务标记暂停 |

原则：**移动是本地动作，必须由每个客户端自己执行**。服务端只发事件；插件收到后在空闲时移动，失败要提示并允许手动重试。所有移动写日志，支持短期撤销。

### 8.4 项目目录（Phase 2）

> 第一版只预留配置结构，不实现项目文件树与代码提交。

- 每个具体平台/团队可以配置多个仓库（如服务端 + 公共库，Web + 组件库）。
- 首次开发时引导选择，记住；可在开发会话里随时增删改。
- 路径只存本地；服务端存「仓库标识」（如 GitLab 项目路径），用于生成链接和统计。
- 项目文件树在右栏展示多个根，标明主仓库/依赖仓库。

## 9. 变更、版本与全量页面

### 9.1 版本规则

- 需求每次 `/req-submit` 或 `/req-change` 生成一个不可变版本（v1, v2…），保留 diff 与变更原因。
- 设计每次 `/design-submit` 生成 vN；原型同理。
- 接口文档每次 `/api-doc` 生成版本，并标记是否「已就绪」。
- 代码提交/MR 是不可变链接，只追加，不覆盖。
- 「最新版」是工作视图；历史版本永远可查、可对比、可回滚（回滚也是一次新版本）。

### 9.2 变更影响分析（建议新增）

需求 vN → vN+1 后：

1. 系统根据变更字段判断受影响阶段：范围/验收标准 → 设计、开发、测试；接口 → 前端；设计稿 → 开发、测试。
2. 受影响任务打上「变更待同步」标记，卡片高亮。
3. 各角色确认已同步（按钮或 `/req-sync`），标记才消失。
4. 范围/工时变化需要负责人重新确认排期。

这一步能避免「需求改了，下游还在按旧版做」的常见问题。

### 9.3 全量页面（Living Spec）

每个需求有一个持续更新的页面：

- 需求总述（最新版）+ 版本历史；
- 原型（最新 + 历史）；
- 设计稿（最新 + 历史）+ 设计组件引用；
- 接口文档（最新 + 就绪状态）；
- 按平台组展示各端卡片：状态、负责人、计划/实际时间、接口文档、设计版本、依赖/阻塞、最近更新、提交链接；
- Bug 列表与复测状态；
- 时间线与日志。

建议再加一个部门级「产品全量」页面：按迭代/模块聚合最新需求页，方便新人和跨组了解业务。Phase 2。

### 9.4 迭代信息变更

- 迭代号/名称/阶段时间/范围都可改。
- 每次修改写事件，通知受影响成员。
- 范围锁定后（开发开始），增删需求需要负责人确认，并记录原因。
- 阶段时间变更时，检查是否有任务的计划时间超出新窗口，给出冲突提示。

### 9.5 数据留存：只沉淀结果

原则：**提交即沉淀**。服务端只在用户明确「提交 / 交付 / 确认」时写入；不记录过程草稿和完整会话。

```text
本地（过程数据）                        服务端（沉淀数据）
会话全文 / 草稿 / 多版原型草稿  ──提交──▶  已确认版本 / 交付物 / 事件元数据 / L1+ 记忆
```

| 数据 | 位置 | 是否上服务端 | 说明 |
|---|---|---|---|
| 个人完整会话 | 本地 DSH | 否 | 不采集、不上传；记忆只上传提炼结果 |
| 需求草稿、原型草稿、设计草稿 | 本地 | 否 | 本地版本历史；可以多次尝试 |
| 已提交的需求版本 | 服务端 | 是 | v1, v2… 不可变快照 |
| 已交付的原型/设计稿 | 服务端/对象存储 | 是 | 只存确认交付的版本 |
| 接口文档、代码提交、MR | 服务端 | 是 | 链接/元数据，不存代码全文 |
| 状态变更、指派、提交 | 服务端 | 是 | 事件元数据，不含对话内容 |
| 测试用例、Bug、附件 | 服务端 | 是 | 提交后沉淀 |
| 记忆 L0 原始对话 | 本地 | 否 | 只在本机 |
| 记忆 L1–L3 | 服务端 | 是 | 提炼、审核、带来源 |

落地规则：

- 工作台的「保存草稿」只写本地；「提交/交付」才调用服务端。
- 设计画布每轮自动版本只留本地；提交时选择一版上传，成为服务端 vN。
- 服务端日志只记 who / what / when / target / 摘要；不存消息正文。
- 记忆抽取在本地完成，或只上传脱敏后的结论；原文不出本机。
- 明确告知用户：换机器后本地草稿不跟随；需要保留就提交或导出。
- 服务端按对象设置保留期与备份；本地提供清理与导出。

## 10. 技术架构

### 10.1 总体架构

```text
┌─ DSH 客户端（每个成员一台）─────────────────────────────┐
│  dsh-workbench 插件                                      │
│   ├─ 页面：迭代/需求/我的工作台/设置                      │
│   ├─ 右栏：DSH Design Studio（需求/设计）+ 开发/测试/Bug 工作台 │
│   ├─ 技能：/req-submit /design-submit /dev-ready-for-test …│
│   ├─ 工具：workbench_*（所有写操作的唯一入口）             │
│   └─ 本地：会话全文、草稿、文件夹、代码仓库、L0 记忆        │
└───────────────────────┬─────────────────────────────────┘
                        │ HTTPS + 短期 token
┌───────────────────────▼─────────────────────────────────┐
│  工作台服务端（公司内网，Docker 部署）                     │
│   ├─ 钉钉 OAuth / 组织架构 / 权限                          │
│   ├─ 平台/角色配置（PlatformGroup / Platform）              │
│   ├─ 只存沉淀：已提交版本/交付物/事件元数据/L1+ 记忆        │
│   ├─ GitLab Webhook / 提交与 MR 关联                       │
│   ├─ 钉钉通知（工作通知 / 群机器人）                       │
│   └─ 对象存储（设计稿、录屏、附件）或外部链接               │
└───────────────┬───────────────────────┬─────────────────┘
                │                       │
          钉钉开放平台                GitLab
```

### 10.2 技术选型建议

| 部分 | 建议 | 理由 |
|---|---|---|
| DSH 插件 | TypeScript，Cordis 插件；server + client 两个入口 | 和 design-studio 同构，易复用 |
| 服务端 | Node.js（Fastify/NestJS）+ PostgreSQL | 团队熟悉、事务与权限好做 |
| 平台/角色配置 | 服务端配置表 + 管理端 | 支持服务端/前端多团队、中台可选，平台可归档 |
| 本地缓存 | SQLite 或 JSON（只读缓存） | 离线可看，断网不阻塞 |
| 文件 | 对象存储（MinIO/S3）或外部链接 | 录屏/设计稿体积大 |
| 实时 | SSE/WebSocket + 轮询兜底 | 工作台状态刷新 |
| 部署 | Docker Compose，内网 | 简单、可备份 |
| 通知 | 钉钉工作通知 + 群机器人摘要 | 复用现有 dsh-dingtalk 生态 |

### 10.3 已在本地核实的技术事实

- 本机 DSH `0.2.2-rc.5`；插件通过 `apply(ctx)` 注册，`inject` 声明依赖。
- 插件可注册：工具（`ctx.tools.register`）、HTTP 路由（`ctx.webServer.register`）、事件（`ctx.on('session/event')`）、右栏标签（`sidebarRightTabs.register`）、右栏面板 slot（`sidebar.right.pane.tab`）、技能 provider、聊天模式 preset。
- DSH bundle 中存在 `sessions.create`、`renameSession`、`additionalDirectories` 等能力；公开插件 API 的稳定性需要 POC 验证。
- dsh-design-studio 0.29.0（MIT）已实现右栏画布、会话级预览、版本历史、设计体检、导出；可作为上游参考或可选依赖，自有改造按需复用其画布/预览模块，并记录上游版本。
- dsh-mnemon（MIT）提供 `extension-sdk`、Sources/Strategies、Memory Spaces、Git 同步；适合做上下文编排与部门 Source。
- dsh-mmpl 展示了另一条路：外部记忆服务（Rust/DuckDB + 向量检索）+ 原生薄桥接；用 `ctx.systemPrompt.section()` 注入热记忆、`ctx.on('session/event')` 每轮捕获；侧栏页面用 `main` + `sidebar.panellist` 槽注册。部门记忆可借鉴其 L0–L3 分层与遗忘/归档模型。

### 10.4 关键数据流

```text
技能（主入口）/ 少数 UI 写入口 → workbench_* 工具 → 服务端校验/权限/事务
  → 写对象 + 写事件
  → 返回最新对象
  → 插件刷新工作台/右栏
  → 服务端发钉钉通知 / SSE 推送
```

- 服务端是唯一写入方；客户端不直接改共享数据。
- 所有写操作幂等（带 requestId），避免重复提交。
- 冲突用版本号/乐观锁；冲突时提示刷新，不静默覆盖。

### 10.5 安全与权限

- 钉钉 AppSecret、GitLab token 只在服务端；客户端 token 短期、可撤销。
- 权限在服务端校验，不能只靠前端隐藏按钮。
- 本地文件夹操作限制在用户选择的顶级文件夹内，防路径穿越。
- 审计日志不可改；敏感操作（封板、移出迭代、转交）单独记录。
- 插件通过公司内网 npm/tgz 分发；版本锁定，避免 RC 升级破坏。

## 11. 分期与第一版范围

> 已确认：第一版只做「需求 + 设计」。开发、测试、封板不进入第一版，但数据模型和页面结构要预留。

### Phase 0：技术验证（1–2 周）

| POC | 成功标准 |
|---|---|
| 插件页面 + 右栏 | 左栏出现「研发工作台」，会话右栏能打开需求面板 |
| 会话创建/命名/跳转 | 点「新建需求」能创建指定文件夹的会话、命名并跳转 |
| 需求文件夹 | 在个人顶级文件夹下按迭代/需求建目录并落盘 |
| 钉钉登录 | Mock Provider 可登录，身份/部门/权限正确；正式 Provider 接口与配置项就位 |
| 设计画布集成 | 技能能调用设计画布，原型/设计稿出现在右栏 |
| 团队服务端 | 两人同时登录，能看到同一迭代和需求，权限生效 |
| 只沉淀结果 | 服务端数据库/存储中没有会话全文和过程草稿；只有提交版本、交付物、事件元数据 |

> 任一项失败，先调整方案再进入 Phase 1；不要在 POC 未过时堆页面。

### Phase 1：需求 + 设计闭环（建议 4–6 周）

**范围**

- 钉钉登录（Mock Provider + 可切换正式 Provider）、多身份（职能 + 具体平台/团队，可多选）、个人顶级文件夹。
- 平台配置：默认种子（服务端/前端/客户端，中台可选），管理员可增删改/归档；身份选择和矩阵都用它。
- 迭代列表/详情/阶段/日志/范围摘要（排期与范围调整走 `/iteration-plan`；只启用需求与设计阶段）。
- 产品：建需求（只填名称）→ 后台建文件夹/会话 → DSH Design Studio 需求上下文 → `/req-draft` / `/req-submit` → v1。
- 需求变更：`/req-change` → v2、diff、日志、通知。
- 设计可选/默认并行：skill 询问是否需要设计，不做三态；明确等待设计时用任务状态「等待设计」。
- 设计：需求卡显示设计状态 → 会话 skill 认领/指派 → 设计会话 → DSH Design Studio → `/design-submit` → v1/v2。
- 需求全量页：总述、原型、设计稿、按平台组的各端卡片、版本历史、日志。
- 团队服务端：登录、权限、对象存储、审计。
- 技能库最小版：内置产品/设计技能、目录、版本固定、启用/停用。
- 数据留存：服务端只存提交版本、交付物、事件元数据。
- 通知：设计指派、需求变更（先站内，钉钉可选）。

**不做**

- 开发任务、工时评估、项目目录、代码提交、提测、接口文档。
- Bug、测试用例、自动录屏、封板。
- 记忆系统的实现（架构见 §7，Phase 2）。
- 技能的个人上传/审核（Phase 2）。
- 需求移出迭代的自动迁移（先提示 + 手动；Phase 2 自动化）。

**验收**

- 一个真实迭代、2–3 个需求、1 个产品 + 1 个设计师跑通；其中至少一个需求不需要设计，一个设计在评审后并行交付；至少一个需求涉及两个平台/团队，矩阵按组展示。
- 平台配置能新增/改名/归档，身份选择和阶段矩阵随之变化。
- 需求 v1/v2、设计 v1/v2、日志、权限都正确。
- 原型和设计稿能在需求全量页看到并追溯。
- 服务端没有会话全文和过程草稿；只有提交版本、交付物、事件元数据。
- Mock 登录可完整跑通；切换正式钉钉只改配置。
- 技能库能查看、启用、固定版本。
- 全程不需要手工改数据库；没有密钥落在客户端；权限在服务端生效。

### Phase 2：开发与提测（4–6 周）

- 工时评估、项目目录、开发工作台。
- 技能管理完整版：个人上传、审核、版本 diff/回滚、按平台组/平台的技能包、code review / 按设计稿开发技能、使用统计。
- 服务端接口文档、代码提交、提测。
- 两个服务端团队 + Web + 1 个移动端试点（按实际平台配置调整）。
- GitLab 集成（commit/MR 链接、Webhook）。
- 变更影响分析扩展到开发。
- 部门记忆（mnemon Source / mmpl 分层）。

### Phase 3：测试、Bug 与封板（4–6 周）

- 测试用例、Bug 提出/修复/转交/复测。
- 自动录屏（Web 先行，移动端后续）。
- 封板检查与报告。
- 通知完善（钉钉工作通知/群摘要）。

### Phase 4：规模化（后续）

- 发版/部署记录、Release 对象。
- 度量：需求周期、提测准时率、Bug 密度、返工率。
- 多部门/多项目空间。
- CI/CD、监控、线上问题回流。
- 移动端自动录屏与真机集群。

## 12. 关键决策

### 已确认（2026-11-22）

| 决策 | 结论 |
|---|---|
| 共享数据 | **团队服务端**（内网部署；DSH 插件是主界面） |
| 身份模型 | **多身份**（职能 + 可配置平台/团队，可多选，权限并集） |
| 平台模型 | **两级可配置**：PlatformGroup + Platform；服务端/前端可多团队，中台可选，归档不删除 |

| 技能管理 | **独立模块**：版本、角色/平台技能包、个人上传与审核 |
| 钉钉接入 | **先 Mock Provider**，拿到凭据后切正式 |

## 14. 建议下一步

1. **按「需求 + 设计」写第一版 PRD**：页面、字段、状态、技能、权限、接口。
2. **做 Phase 0 的 POC**，重点是「会话创建/命名/跳转」「需求文件夹」「钉钉登录」「设计画布」。
3. **在当前目录搭工程骨架**：DSH 插件 + 团队服务端 + 共享类型；先跑通一条需求+设计链路。
4. **选试点**：一个产品 + 一个设计师 + 一个真实迭代、2–3 个需求。
5. **再排后续阶段**：开发/测试/封板分别评审，不一次性铺开；记忆系统按 §7 架构在 Phase 2 接入。

### 15.2 全局组件

- 状态 chip：需求/设计/各平台/测试；颜色区分「未开始 / 进行中 / 已完成 / 阻塞 / 不涉及」。
- 阶段矩阵：按需求实际涉及的平台动态渲染，按平台组分组；平台多时汇总 + 展开，不涉及折叠；必须有列头，不能只靠 tooltip。
- 平台卡：平台组 · 平台/团队、状态、负责人、计划/实际时间、关键产物、依赖/阻塞、最近更新、「进入会话」。
- 版本 diff：需求/设计/技能三类复用同一套对比组件。
- 指派/认领：头像、角色、状态、可认领提示；认领/指派动作在会话 skill，不在 UI 做表单。
- 技能卡：名称、版本、适用角色/平台、状态、使用量。
- 空状态 / 错误状态 / 加载态 / 权限不足 / 服务断开。
- 文件/文件夹选择器（本地路径、多项目）。
- Mock 模式横幅（醒目但不刺眼）。

### 15.3 出图约定

- 桌面端 1440×900；右栏 360–420px；遵循 DSH 现有布局与主题变量，浅色/深色都要。
- 中文界面；文案要能直接用于实现。
- 每个页面标注：默认态、空态、加载态、错误态、无权限态、操作成功/失败提示。
- 第一版不需要出开发/测试工作台细稿，但信息架构里要能看到入口和「Phase 2/3」标记。
- 右栏明确标注复用 **DSH Design Studio**，不重新设计画布；平台配置驱动矩阵和卡片，不要写死平台列。
- 交付 Figma/蓝湖链接 + 组件库 + 标注；如果沿用 design-studio 的设计 token，请注明来源。

## 附录：术语表

| 术语 | 含义 |
|---|---|
| 迭代 | 一次研发周期，包含需求、设计、开发、测试、封板 |
| 需求总述 | 持续更新的业务/功能描述，不是一次性文档 |
| 阶段矩阵 | 按需求涉及的平台动态生成、按平台组分组的状态集合 |
| 平台组 / 平台 | 可配置的两级组织维度；平台挂在组下，可归档 |
| 提测 | 开发完成并提交给测试，附代码链接与自测结论 |
| 封板 | 测试通过、范围冻结，迭代进入只读状态 |
| 产物 | 原型、设计稿、接口文档、提交、MR、用例、录屏等 |
| 工作台 | 插件里的结构化页面/右栏面板；需求/设计右栏基于 DSH Design Studio |
| 技能 | DSH 的 `/xxx` 命令，负责引导对话并调用工具 |
| 记忆 | 部门/项目/迭代/需求/个人的可检索知识 |
