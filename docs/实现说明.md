# dsh-workbench 实现说明

DSH 部门研发工作台的实现细节：**DSH 插件是主界面，Rust 团队服务端保存共享协作数据**。
返回 [`README.md`](../README.md) 看目录结构与快速开始。

覆盖需求、设计、开发、测试、冻结、发布全流程，以及会签评审、需求活文档、附件/设计稿跨设备
存储、技能管理、通知聚合和本机 DSH 会话绑定。

- 主界面：`client.js` + `client.design-studio.js`（DSH 左侧「研发工作台」+ 右侧「需求」面板）
- 本机 BFF：`index.js`（同源 Cookie、转发服务端、管理本机文件夹/DSH 会话映射）
- 团队服务端：`server/`（Rust + axum；SQLite 或 Postgres；可 Docker 部署）
- 设计画布：改造自 `dsh-design-studio@0.29.0`（MIT），已并入工作台插件
- 回归：`server/test-api.sh`（112 项）、`tests/host-bff.mjs`（51 项）、
  `server/test-integrations.sh`（34 项）、`server/test-gitlab-real.sh`（真实 GitLab，20 项/平台）、
  `e2e/`（Playwright 5 项）；审查与修复记录见
  [`REVIEW-2026-11-22.md`](reviews/REVIEW-2026-11-22.md)、
  [`REVIEW-2026-11-23.md`](reviews/REVIEW-2026-11-23.md)

## 架构

```
┌────────────────────────────── DSH 桌面 / Web ──────────────────────────────┐
│  client.js                                                                  │
│    左侧：研发工作台（迭代、需求、通知、技能、平台配置、管理后台）           │
│    右侧：需求、设计两个独立面板（需求上下文 / 设计版本与原型预览）          │
│    会话：技能 / 工具 / 确定性 /wb-* 命令                                    │
│                                                                             │
│  index.js（host BFF，跑在本机）                                             │
│    · 同源 HttpOnly Cookie，转发 Authorization: Bearer                       │
│    · 本机顶级文件夹、需求目录、DSH workspace/session 映射（不上传）         │
│    · 会话认领：DSH session -> 工作台账号；工具/命令按会话归属解析身份       │
│    · 交付设计时把本机设计文件正文上传服务端，其他设备可打开                 │
└───────────────────────────────────┬─────────────────────────────────────────┘
                                    │ HTTP + x-workbench-internal-token
┌───────────────────────────────────▼─────────────────────────────────────────┐
│  Rust 团队服务端（server/，默认 :3210）                                     │
│    axum · SQLite(WAL) / Postgres(JSONB) · JWT · Mock/DingTalk Provider      │
│    用户与角色 · 平台组/平台 · 迭代 · 需求 · 活文档 · 附件/设计稿            │
│    会签 · 设计版本 · 开发/测试/发布 · 技能审核 · 通知聚合 · 事件/审计       │
│    钉钉组织同步/工作通知 · GitLab 分支/MR/流水线 · Webhook                   │
└─────────────────────────────────────────────────────────────────────────────┘
```

**服务端只保存已定稿的协作数据**：需求版本、活文档、评审结论、设计版本与设计稿正文、
附件、开发/测试/发布记录、技能、通知和事件。对话原文、草稿、本机路径和原始 DSH 会话 ID
不进入服务端（设计稿正文是用户明确交付的产物，属于例外）。

## 快速开始

### 1. 启动 Rust 服务端（SQLite）

```bash
cd server
cargo run
# 默认 http://127.0.0.1:3210，数据库 ./data/workbench.db，首次启动自动写入演示数据
```

### 2. 或用 Docker Compose（Postgres）

```bash
bash deploy/init-env.sh     # 生成随机密钥的 .env（权限 600），已存在则不覆盖
docker compose up -d --build
curl http://127.0.0.1:3210/health
# {"ok":true,"database":"postgres",...}
```

Compose 默认启动 `postgres:16-alpine` + 服务端，数据在命名卷 `workbench-pg`。
容器带健康检查；`docker compose restart workbench-server` 后数据仍在。端口只发布到
宿主机回环地址 `127.0.0.1:3210`，可用 `WORKBENCH_PORT=3220 docker compose up -d` 改端口。
`.env` 中的 `POSTGRES_PASSWORD` / `WORKBENCH_AUTH_SECRET` / `WORKBENCH_INTERNAL_TOKEN`
由脚本随机生成；缺少时 compose 直接报错，不会使用默认弱密钥。

Postgres 密码只在命名卷首次初始化时生效；卷已存在时修改 `.env` 的 `POSTGRES_PASSWORD`
不会改库内密码。需要重置卷，或进入容器执行
`ALTER USER workbench WITH PASSWORD '<新密码>';`。

生产环境必须设置 `APP_ENV=production`、`WORKBENCH_AUTH_PROVIDER=dingtalk`、强随机
`WORKBENCH_AUTH_SECRET` / `WORKBENCH_INTERNAL_TOKEN` / `POSTGRES_PASSWORD`，并在反向代理上
启用 HTTPS。Compose 中 `WORKBENCH_INTERNAL_ALLOW_REMOTE=1` 是因为 DSH 宿主从宿主机经回环
端口访问容器、容器看到的来源是 Docker 网关；端口本身只绑定 `127.0.0.1`。如果改为反向代理
或跨机部署，应使用网络隔离 + mTLS，并只允许 DSH 宿主访问服务端。

### 3. 可选：本地真实 GitLab

仓库带了 `deploy/gitlab/`（GitLab CE 17.11.4 + Runner），用来验证真实分支/MR/流水线/
Webhook。默认端口 `8929`，首次启动约 3–8 分钟：

```bash
mkdir -p .local
# 用随机值替换示例占位值
sed -e "s|^GITLAB_ROOT_PASSWORD=.*|GITLAB_ROOT_PASSWORD=$(openssl rand -hex 24)|" \
    -e "s|^GITLAB_WEBHOOK_SECRET=.*|GITLAB_WEBHOOK_SECRET=$(openssl rand -hex 32)|" \
    deploy/gitlab/gitlab.env.example >.local/gitlab.env
chmod 600 .local/gitlab.env
docker compose -f deploy/gitlab/docker-compose.yml --env-file .local/gitlab.env up -d gitlab
bash deploy/gitlab/bootstrap.sh
# 把脚本输出的 RUNNER_TOKEN 写回 .local/gitlab.env，再启动 runner
docker compose -f deploy/gitlab/docker-compose.yml --env-file .local/gitlab.env up -d runner
```

初始化脚本会创建机器人、私有分组 `workbench`、项目 `trade-server`/`web`、CI 文件、
Group Runner 和 Webhook，凭据写入 `.local/gitlab.outputs.env`（已在 `.gitignore` 里）。
完整步骤见 [`deploy/gitlab/README.md`](../deploy/gitlab/README.md)。

### 4. 安装并启动 DSH 插件

```bash
# 独立 profile，避免影响桌面默认 profile
REPO_ROOT="$(git rev-parse --show-toplevel)"
# 首次建 profile；已存在时不要再带 --from-default-profile，否则会覆盖成默认 web profile
[ -d ~/.dsh/profiles/workbench-poc ] || \
  dsh --profile workbench-poc --from-default-profile web --dump-config >/dev/null
dsh plugin --profile workbench-poc add "$REPO_ROOT"

WORKBENCH_SERVER_URL=http://127.0.0.1:3210 \
WORKBENCH_INTERNAL_TOKEN="$(grep '^WORKBENCH_INTERNAL_TOKEN=' .env | cut -d= -f2)" \
DSH_WORKBENCH_BASE="$REPO_ROOT/runtime/workbench" \
dsh --profile workbench-poc --no-open --port 3199
```

打开终端输出的带 token URL，左侧出现「研发工作台」。Mock 模式点一个种子用户即可登录，
然后完成首次引导：默认身份、负责平台、本机顶级文件夹。

## 环境变量

**Rust 服务端**

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `APP_ENV` | `development` | `production` 时强制钉钉登录并拒绝默认密钥 |
| `PORT` | `3210` | 监听端口 |
| `DATABASE_PATH` | `./data/workbench.db` | SQLite 路径；设置 `DATABASE_URL` 时改用 Postgres |
| `DATABASE_URL` | 空 | Postgres 连接串，例如 `postgres://workbench:pass@postgres:5432/workbench` |
| `WORKBENCH_AUTH_PROVIDER` | `mock` | `mock` / `dingtalk` |
| `WORKBENCH_AUTH_SECRET` | POC 默认值 | JWT HS256 签名密钥；生产必填 |
| `WORKBENCH_INTERNAL_TOKEN` | POC 默认值 | host BFF 与服务端之间的内部令牌；生产必填 |
| `WORKBENCH_PUBLIC_URL` | 空 | 对外 HTTPS 地址，用于钉钉工作通知链接；空则不附链接 |
| `WORKBENCH_ALLOWED_ORIGINS` | 空 | 浏览器跨域 Origin 白名单（逗号分隔）；空表示不启用 CORS |
| `WORKBENCH_BIND_ADDR` | `127.0.0.1` | 监听地址；生产绑定非回环地址需同时设置 `WORKBENCH_INTERNAL_ALLOW_REMOTE=1` |
| `WORKBENCH_INTERNAL_ALLOW_REMOTE` | `0` | `1` 时允许非回环来源使用内部令牌（Docker 场景） |
| `WORKBENCH_TOKEN_TTL_SECONDS` | `604800` | 登录 JWT 有效期（7 天） |
| `DINGTALK_CLIENT_ID` / `DINGTALK_CLIENT_SECRET` | 空 | 钉钉应用凭据，只放服务端 |
| `DINGTALK_AGENT_ID` | 空 | 钉钉应用 AgentId；发送工作通知时必填 |
| `DINGTALK_WORK_NOTIFY` | `0` | `1` 时把站内通知同步为钉钉工作通知 |
| `DINGTALK_API_BASE` | `https://oapi.dingtalk.com` | 测试时可指向本地 mock |
| `DINGTALK_DEFAULT_ROLES` | `dev` | 钉钉同步新建成员的默认角色 |
| `DINGTALK_SYNC_ROOT_DEPT` | `1` | 组织同步根部门 ID |
| `DINGTALK_SYNC_DISABLE_MISSING` | `0` | `1` 时同步会停用钉钉中已不存在的成员；组织数据不完整时不要开启 |
| `GITLAB_BASE_URL` | 空 | GitLab 地址；配置后启用分支/MR/流水线 |
| `GITLAB_TOKEN` | 空 | GitLab Token，只在服务端使用 |
| `GITLAB_WEBHOOK_SECRET` | 空 | GitLab Webhook `X-Gitlab-Token` |
| `GITLAB_DEFAULT_BRANCH` | `main` | 分支与 MR 的目标分支 |
| `RUST_LOG` | `dsh_workbench_server=info,tower_http=info` | 日志级别 |

**DSH host**

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `WORKBENCH_SERVER_URL` | `http://127.0.0.1:3210` | Rust 服务端地址 |
| `WORKBENCH_INTERNAL_TOKEN` | POC 默认值 | 必须与服务端一致 |
| `DSH_WORKBENCH_BASE` | `~/DSH-Workbench` | 默认本机顶级文件夹 |
| `WORKBENCH_COOKIE_SECURE` | 空 | HTTPS 部署设为 `1`；生产默认开启 |
| `NODE_ENV` | 空 | `production` 时拒绝默认内部令牌 |

Mock Provider 签发真实 JWT，权限校验与钉钉 Provider 完全一致，Mock 不绕过权限。
钉钉授权码由 Rust 服务端在服务端换取用户信息，`AppSecret` 不会下发到浏览器。

## 页面

### 登录、首次使用与多身份

- 登录页：Mock 用户列表或「使用钉钉登录」；错误明确。
- 首次引导：默认身份（角色权限取并集）、负责的平台、本机顶级文件夹。
- 个人设置：随时改身份/平台/文件夹；退出登录清 Cookie。
- **会话身份隔离**：浏览器打开某个 DSH 会话时认领它；工具/命令按会话归属解析账号。
  换一个账号打开同一会话会被拒绝，不再有进程级「最后登录用户」串号。

### 研发工作台

- 迭代选择器、新建迭代、迭代设置（名称/阶段/状态/日期/默认会签人/归档）。
- 7 个统计卡：需求总数、本期范围、待评审、开发中、待测试/测试中、已发布、设计已更新。
- 需求列表：状态、设计状态、范围、负责人、平台、开发进度、最近测试、发布版本、计划日期。
- 需求详情：活文档编辑、团队文件/附件上传、会签进度、开发任务卡（平台/负责人/分支/MR/
  流水线）、测试轮次、发布版本、设计版本/文件数、会话列表（进入/归档/恢复/解绑本机）。
- 通知铃：按需求聚合筛选、未读徽标、单条已读、全部已读；已读状态保存在服务端，多设备同步。
- 技能管理：团队/个人技能、角色包、版本历史、负责人审核、归档/恢复、上传新版本。
- 管理后台（admin）：
  - 用户与角色：修改姓名、角色、平台、启用/停用。
  - 钉钉同步：触发组织架构/成员同步，返回新增/更新/停用数量。
  - 集成状态：钉钉、GitLab、Webhook、Postgres 配置状态（不返回任何密钥）。
  - 审计事件：最近管理操作。
- 平台配置：平台组/平台、排序、负责人、GitLab 项目 ID/路径、归档/恢复。

### 需求、设计（右侧栏两个独立面板）

- 「需求」面板：顶部需求条（编号、标题、状态、设计状态、范围、计划日期、会签/开发/测试/
  发布摘要）、需求活文档（摘要、验收标准、正文）、会话列表和版本历史。设计稿数量只作为
  元数据展示，具体文件在「设计」面板查看。
- 「设计」面板：原型与预览图列表。原型优先用设计师本机文件，其他角色用团队服务端保存的
  交付版本；预览走工作台自己的同源沙箱路由 `/dsh-workbench/api/design-preview`，按 1440
  宽等比缩放，任何角色、任何设备都能直接看到完整设计稿，不再依赖 Design Studio 的随机
  端口预览服务。预览图（PNG）同样直接打开。
- 设计交付走会话：交付时自动把本机 HTML/CSS/JS/SVG 等设计资产上传服务端，其他设备在
  「设计」面板看到同一份交付版本。开发开始后交付或二次交付会标记「设计已更新」。
- 右侧栏的「+」菜单里，「需求」「设计」是两个独立入口；Design Studio 工具（`preview_page`
  等）仍可在会话里使用，但不再和需求面板挤在同一个 tab。

## 生命周期

| 当前状态 | 动作 | 结果 |
| --- | --- | --- |
| 草稿 | 提交 `/req-submit` | 待评审，需求版本 +1 |
| 待评审 | 会签 `/req-review approve` | 全部会签人通过 → 已通过 |
| 待评审 | 退回 `/req-review reject` | 待修改，移出本期范围 |
| 已通过 | 排期 `/req-schedule` | 已排期，记录计划日期并纳入本期 |
| 已通过/已排期/开发中 | 范围移出 `/req-scope out` | 暂缓，记录原因 |
| 暂缓 | 范围纳入 `/req-scope in` | 有排期则回到已排期，否则已通过 |
| 已排期 | 开始开发 `/dev-start` | 开发中；配置 GitLab 时自动建分支 |
| 开发中 | 完成开发 `/dev-finish` | 所有平台完成 → 待测试；配置 GitLab 时建 MR 并查流水线 |
| 待测试 | 开始测试 `/test-verify start` | 测试中 |
| 测试中 | 测试通过 / 不通过 | 测试通过 / 测试不通过（通知开发） |
| 测试通过 | 冻结 `/release-freeze freeze` | 已冻结 |
| 已冻结 | 发布 `/release-freeze release 版本号` | 已发布，记录版本 |

设计是可选并行轨：可以一直不认领，也可以在开发开始后交付；服务端记录设计版本、
交付人和时间，工作台展示设计文件数和晚到提示。

## 会话内写操作

技能由模型按指令调用工具，是正式交互方式；`/wb-*` 是确定性回归命令，不依赖模型。

| 技能 | 工具 | 说明 |
| --- | --- | --- |
| `/req-submit` | `workbench_submit_requirement` | 提交需求，版本 +1 |
| `/req-document` | `workbench_update_document` | 写需求摘要、正文与验收标准 |
| `/req-review` | `workbench_review_requirement` | 通过/退回，多会签人 |
| `/req-reviewers` | `workbench_set_reviewers` | 设置会签人 |
| `/req-schedule` | `workbench_schedule_requirement` | 排期 |
| `/req-scope` | `workbench_scope_requirement` | 纳入/移出本期 |
| `/req-move` | `workbench_move_requirement` | 跨迭代移动并重新编号 |
| `/iteration-plan` / `/iteration-edit` | `workbench_iteration_status` / `workbench_iteration_update` | 迭代概览与编辑、归档 |
| `/design-claim` | `workbench_claim_design` | 认领设计 |
| `/design-start` | `workbench_design_context` | 读取上下文 + 加载设计能力 |
| `/design-deliver` | `workbench_deliver_design` | 交付设计版本并上传设计稿 |
| `/dev-assign` | `workbench_dev_action` | 按平台指派/认领 |
| `/dev-start` / `/dev-finish` | `workbench_dev_action` | 开始/完成开发（GitLab 已配置时真实建分支/MR） |
| `/test-verify` | `workbench_test_action` | 开始/通过/不通过 |
| `/release-freeze` | `workbench_release_action` | 冻结/解冻/发布 |

确定性命令：`/wb-submit`、`/wb-review`、`/wb-schedule`、`/wb-scope`、`/wb-dev`、`/wb-test`、
`/wb-release`、`/wb-iteration`、`/wb-claim`、`/wb-deliver`、`/wb-status`。
省略需求编号时使用当前会话绑定的需求。命令结果显示为工作台 toast，不进入模型对话。

## 权限

| 操作 | 允许身份 |
| --- | --- |
| 迭代编辑/归档、平台配置、技能团队发布与审核、管理后台 | lead / admin |
| 新建需求、需求会话、评审/排期/范围/移动、编辑需求活文档 | product / lead / admin |
| 设计会话、认领设计、设计稿上传 | design / lead / admin |
| 开发会话、认领/开始/完成开发 | dev / lead / admin |
| 测试会话、测试结论 | qa / lead / admin |
| 冻结/发布 | lead / admin |
| 上传普通附件、查看状态 | 任何已登录用户 |

会签：迭代可配置多名会签人；只有待评审状态、且未重复投票的会签人可以评审。全部通过才算
通过，任一退回即退回。管理员可代为处理；不在名单里的负责人不能代替投票（可在迭代设置里
调整会签人名单）。

## HTTP API

### 团队服务端（Rust，直连 `:3210`）

公开：`GET /health`、`GET /auth/config`、`POST /auth/mock`（仅 Mock）、
`GET /auth/dingtalk/start`、`GET /auth/dingtalk/callback`。

需要 `Authorization: Bearer <JWT>`（或 host 的内部令牌 + `x-workbench-actor`）：

- `GET /state`：用户、平台、迭代、当前迭代需求、通知、通知聚合、未读数、技能。
- `GET /requirements/by-session/:recordId`：按会话反查需求。
- `POST /onboarding/complete`、`POST /iterations`、`POST /iterations/:id`、
  `POST /iterations/:id/select`、`POST /iterations/:id/archive|restore`。
- `POST /requirements`、`POST /requirements/:id/bind`、`POST /requirements/:id/create-failed`。
- `POST /requirements/:id/sessions`：记录需求/设计/评审/开发/测试会话元数据。
- `POST /requirements/:id/sessions/:recordId/archive|restore`：会话归档/恢复。
- `POST /requirements/:id/document`：编辑需求活文档（摘要/验收标准/正文）。
- `POST /requirements/:id/artifacts`：上传附件/设计稿；`GET /artifacts/:id` 读取正文。
- 生命周期：`submit`、`review`、`reviewers`、`schedule`、`scope`、`move`、
  `design-claim`、`design-deliver`、`dev-assign|claim|start|finish|reopen`、
  `test-start|pass|fail`、`freeze|unfreeze|release`。
- 平台：`POST /platform-groups`、`/platforms` 及 `:id` 编辑、`archive`、`restore`。
- 技能：`GET /skills`、`GET /skills/published`、`POST /skills`、
  `POST /skills/:id`、`POST /skills/:id/versions`、`POST /skills/:id/review`。
- 通知：`GET /notifications`、`POST /notifications/read`。
- 事件/审计：`GET /events`、`GET /audit`（管理员）。
- 管理：`POST /admin/users/:id`、`POST /admin/dingtalk/sync`、`GET /admin/integrations`。
- 集成：`POST /webhooks/gitlab`（校验 `X-Gitlab-Token`）。

### DSH host BFF（浏览器同源 `/dsh-workbench/api`）

浏览器只访问 host。host 负责 Cookie 鉴权、转发服务端、补齐本机需求目录，并在创建会话时
回写本机映射。主要路由：`/auth/*`、`/state`、`/requirement`、`/onboarding/complete`、
`/folders/ensure`、`/requirements`、`/requirements/:id/sessions`、`/requirements/:id/bind`、
`/requirements/:id/sessions/:recordId/unbind`、`/sessions/claim`，其余路由按原路径透传。
`POST /requirements/:id/sessions` 是唯一同时写服务端记录和本机映射的路由：服务端只拿到
会话类型与标签，DSH 会话 ID/工作区/路径留在本机。

设计稿预览接口在 `/dsh-workbench/api/design-preview`（host BFF 提供）：交付版本向团队服务端
取产物，本机文件只读当前用户需求文件夹内的文本/图片；HTML/CSS/JS/SVG 响应带沙箱 CSP，
不携带工作台会话能力。Design Studio 自己的 `/dsh-design-studio/api/*` 仍保留给会话工具。

## 安全边界

- 浏览器 Cookie：HttpOnly、SameSite=Lax，生产默认 Secure；写请求校验 Origin/Sec-Fetch-Site。
- 内部令牌：服务端默认只接受回环地址；Docker 场景需显式开启远程并做网络隔离。
- CORS：默认关闭，只有 `WORKBENCH_ALLOWED_ORIGINS` 白名单启用。
- 路径：本机顶级文件夹/需求目录做 realpath + 符号链接检查，拒绝路径穿越。
- 密钥：钉钉 AppSecret、GitLab Token 只在服务端环境变量；集成状态 API 不返回密钥。
- 附件：正文存服务端，浏览器通过 host 取回后用 Blob 打开，不由服务端同源直接渲染 HTML。
- 生产：拒绝 `mock` Provider 和默认密钥；要求 HTTPS、强随机密钥和反向代理限流。

### 5. 多角色容器仿真（kiri）

（`http://127.0.0.1:3425`）的 **Hy4 Flash** 模型（容器内通过
`host.docker.internal:3425` 访问），启动 6 个角色容器，走完一个需求的完整生命周期。

```bash

node deploy/dsh-sim/run-sim.mjs --resume S11-018
```

## 已知限制与后续

- **Postgres 仍是整份 JSONB 快照**：已支持多实例部署的行锁 + 版本号，但每次变更写全量状态；
  数据量上来后应把 requirements/events/notifications/artifacts 拆成独立表做增量写。
- **SQLite 单实例**：进程内互斥，适合本地演示和小团队；正式多实例请用 Postgres。
- **钉钉真实授权未跑**：代码路径完整，组织同步/工作通知用本地 mock 验证；需要企业
  AppKey/AppSecret/AgentId 才能跑真实租户。离职停用同步已实现，默认关闭；确认组织数据完整后再开启。
- **GitLab 已本地真实联调，生产实例仍需配置**：本地 GitLab CE 17.11.4 + Runner 已验证
  分支/提交/流水线/MR/Webhook；外部生产实例还需按实际 HTTPS、分支保护、审批规则和共享
  Runner 调整。CI 目前只回写 GitLab pipeline 状态，没有接 Jenkins/制品库。
- **设计稿上传限制**：自动上传只处理 HTML/CSS/JS/SVG/JSON/MD/TXT，单文件 1.5 MB、最多 30 个；
  二进制设计资产可通过「上传附件」手动上传（3 MB）。
- **附件上限**：单文件 3 MB（解码后），每条需求最多 100 个、合计 50 MB，存在状态快照里；
  大文件应改用对象存储。
- **监控**：提供 `/health`、Docker healthcheck 和 tracing 访问日志；没有 Prometheus 指标端点。
- **技能治理**：技能正文由人上传，模型是否遵守取决于提示词；没有技能沙箱/权限执行隔离。
- **设计画布保留 Design Studio 能力**：内嵌后保留首页、画布、外观、体检、导出、版本等能力，
  只去掉工作台不需要的独立聊天框/市场入口；上游升级需要重新合入 `design-studio/` 与
  `client.design-studio.js` 的改动，详见这两个文件的顶部注释。
- `client.design-studio.js` 是 DSH package-local chunk，必须与 `client.js` 同目录且匹配
  `client.*.js`。
- **内部令牌仍是机器凭据**：生产需要网络隔离/mTLS 或只在 DSH 宿主上暴露服务端端口。
- **JWT 无吊销**：退出登录只清 Cookie，已签发的令牌在 TTL 内仍有效；生产需吊销表或短 TTL + 刷新令牌。
- **无内置限流**：登录、Mock 登录和 Webhook 依赖反向代理限流；生产需在网关层配置。
- **附件按团队可见**：需求状态对全员可见，附件正文同样按已登录成员可读；如需按需求授权，应先引入需求级 ACL。
- **工具身份基于会话认领**：DSH 会话首次在浏览器认领后，工具以认领人身份执行；生产可替换为短期 capability。
- **仓库根目录**：插件代码就在仓库根目录，安装时用 `git rev-parse --show-toplevel`
  取绝对路径；`.env`、数据库和 `server/target` 已忽略。

更完整的设计取舍与验证结论见 [`POC结论.md`](POC结论.md)。
